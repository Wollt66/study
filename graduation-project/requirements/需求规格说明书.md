## 1. 项目概述

### 1.1 项目背景

本项目为本科毕业设计选题"城市交通监控大屏（全栈版）"。v1.0 版本采用纯前端技术路线，由前端内置模拟引擎离线生成全部数据；v2.0 在此基础上引入自建后端与数据库，形成"数据持久化 + 服务端聚合 + 实时推送 + 双角色权限"的完整全栈链路，同时**保留原模拟引擎作为离线兜底**，使答辩演示既可展示全栈能力，也可在断网或无数据库环境下独立完成。

系统面向两类使用者：**访客**直接浏览免登录的大屏；**管理员**登录后在管理后台维护路网数据并查看聚合看板。大屏集中呈现城市交通运行态势：地图路况热力与事故分布、核心运行指标、路口流量排行、事故构成、车辆结构、分时流量规律。

系统以五大技术能力作为毕业设计的核心亮点：

1. **地图逐级钻取**：中国地图 → 省级 → 市级逐级下钻，展示路况热力与事故分布散点，支持逐级返回；
2. **多图表联动**：点击地图某省/某市、某图表图例或某车辆类型后，大屏内全部图表自动按所选维度过滤刷新；
3. **实时数据刷新**：服务端采集器按周期产出数据，经 SSE 推送至大屏，图表以平滑过渡动画呈现变化，支持暂停/恢复；
4. **全栈数据链路**：Node.js API 提供鉴权、路网管理、看板聚合、历史趋势与实时推送五项能力，数据落库 MySQL 并支持历史回溯；
5. **数据源可切换**：默认纯 HTTP 走后端，`VITE_DATA_SOURCE=mock` 时退回前端模拟引擎，保证演示环境无关性。

### 1.2 项目目标

1. 交付一块信息密度高、交互流畅、视觉风格鲜明的城市交通监控大屏，视觉版式与 v1.0 保持一致（仅替换数据来源）；
2. 实现全国—省—市三级地图钻取与全图表联动过滤，模拟"指挥中心态势研判"的完整交互链路；
3. 实现服务端实时数据生产与推送，同时保留可离线运行的模拟引擎兜底，支持演示节奏控制（暂停/恢复）；
4. 交付可用的管理后台：管理员登录后可维护路网区域与路口、查看看板聚合与历史趋势；
5. 以 1920×1080 为设计基准实现大屏等比自适应缩放，满足答辩现场不同显示设备的投放需求；
6. 保证既有论文与答辩材料引用的数据质量指标（连续性、双峰、口径闭合）在改造后仍可复现。

### 1.3 项目范围

**范围内（系统要做）：**

- 单页大屏前端应用（一个全屏页面承载全部内容），版式与 v1.0 一致；
- 全国 / 省 / 市三级地图钻取、路况热力、事故散点与逐级返回；
- 全图表联动过滤（地区、图表图例维度、车辆类型三类过滤来源）；
- 前端数据源抽象：HTTP 数据源（默认，含 SSE 推送）与 mock 数据源（离线兜底），通过环境变量切换；
- 服务端五项能力：JWT 登录鉴权、路网区域/路口管理 CRUD、看板聚合查询、历史趋势查询、SSE 实时推送；
- 管理员登录、令牌刷新与登出、失败锁定；
- 数据持久化：MySQL 8 的 10 张表（含种子数据与可重复执行的初始化脚本）；
- 服务端模拟采集器：按周期生产数据、按粒度落库并执行保留期清理；
- 两项角色：访客（免登录，只读大屏）与管理员（登录后进入管理后台）；
- 大屏等比自适应缩放与浏览器全屏模式；
- 赛博朋克霓虹渐变视觉风格与圆角卡片界面（管理后台沿用同源主题）。

**范围外（系统不做，防止范围蔓延）：**

- 不实现用户注册、找回密码、多角色细分（仅访客与管理员两种角色）；
- 不做告警规则配置、告警通知、指挥调度；
- 不做题库、答题、阅卷等教学功能；
- 不提供数据导出、报表打印、批量导入；
- 不接入真实交通数据源或第三方地图服务（路况计算、导航、街景均不做）；
- 不做移动端 / 触摸屏适配（仅面向桌面浏览器与鼠标交互）；
- 不实现多租户、微服务拆分、消息队列、缓存中间件（Redis 等）；
- 不使用 Java / SpringBoot / Maven 技术栈（选型取舍见设计文档）。

### 1.4 术语表

| 术语 | 定义 |
| --- | --- |
| 大屏 | 本系统唯一的人机交互界面：以可视化图表为主体、按 1920×1080 设计稿布局的单页展示页面。 |
| 钻取（下钻） | 从全国地图逐级进入省、市更细粒度地图视图的交互过程，与"返回上一级"相对。 |
| 联动 | 大屏内某一处选择操作（地图区域、图表图例、车辆类型）引发其余图表同步过滤刷新的机制。 |
| 维度 | 数据过滤所依据的角度，本系统主要为：地区维度（全国/省/市）、车辆类型维度、事故类型维度。 |
| 模拟数据引擎 | 内置于前端、离线运行的数据生成模块，按刷新周期产出符合交通业务规律的随机模拟数据，是本系统唯一数据来源。 |
| 刷新周期 | 相邻两次自动推送新模拟数据的时间间隔，默认 5 秒。 |
| 拥堵指数 | 衡量道路拥堵程度的量化指标，取值 0～10，数值越大越拥堵，分级标准见数据质量约束。 |
| 在途车辆 | 统计时刻处于道路通行状态的所有车辆总数。 |
| 路况热力 | 叠加在地图上、以颜色梯度表征区域拥堵强弱的图层。 |
| 事故散点 | 叠加在地图上、以点标记表征事故发生位置与严重程度的图层。 |
| 平滑噪声 | 对随机数据施加的连续性处理，使相邻两批数据的变化平缓、不发生数量级跳变。 |
| 等比自适应缩放 | 以 1920×1080 为基准、按浏览器窗口比例对大屏整体内容进行同比例缩放的适配方式。 |
| EARS | 一种可测试的需求描述句式，本报告功能性需求统一采用"当……时，系统应当……"格式。 |
| 访客 | 未登录的使用者，只能读取大屏数据的只读角色。 |
| 管理员 | 通过账号口令登录、可访问管理后台并执行路网写操作的角色。 |
| 数据源 | 大屏取数的来源实现，分为 `http`（后端 API + SSE）与 `mock`（前端模拟引擎）两种。 |
| 快照（Snapshot） | 某一时刻的全量交通数据集合，包含全国/省/市聚合、路口集合与活跃事故集合；HTTP 与 SSE 使用同一结构。 |
| 采集器 | 后端按周期生产模拟数据并落库、广播的服务端模块。 |
| 访问令牌 / 刷新令牌 | 访问令牌用于接口鉴权（短时效）；刷新令牌用于换取新的访问令牌（长时效、可吊销、使用即轮换）。 |
| 看板聚合查询 | 按区域与业务维度返回 KPI、路口排行、类型占比、地图热力与散点的查询能力。 |
| 历史趋势 | 基于落库快照按时间粒度聚合的时序数据查询能力。 |
| 落库粒度 / 保留期 | 快照写入数据库的时间间隔，以及数据在被自动清理前的保存时长。 |

## 2. 用户角色与场景

### 2.1 用户角色

| 角色 | 角色说明 | 与系统的交互 | 是否需要登录 |
| --- | --- | --- | --- |
| 访客（交通指挥中心值班员 / 答辩评委 / 开发者演示视角） | 大屏的目标使用者，在指挥中心场景下持续监控辖区交通运行态势 | 浏览大屏、钻取/返回地图、切换地区与车辆类型/事故类型过滤维度、暂停/恢复实时刷新、切换全屏 | 否（免登录，只读） |
| 管理员 | 路网数据的维护者与业务看板的使用者 | 登录 / 刷新令牌 / 登出；路网区域与路口的增删改查；查看看板聚合与历史趋势；查看实时推送数据 | 是（账号 + 口令） |

说明：系统只有**访客**与**管理员**两种角色，不存在注册流程与其他角色。访客的全部操作均为只读；管理员在登录后获得写权限。演示场景中的值班员、评委、开发者均以访客身份使用大屏，不构成额外角色。

### 2.2 典型使用场景

**场景 1：答辩主流程演示**
开发者在本机启动大屏并进入浏览器全屏 → 大屏呈现全国地图热力与事故散点、四项 KPI 与各专题图表，数据每 5 秒自动刷新 → 评委示意查看某省 → 开发者点击该省完成下钻，全屏图表联动为该省数据 → 继续下钻某市展示市级视图 → 逐级返回全国。全程离线，数据连续滚动。

**场景 2：多维度联动分析**
值班员注意到某省事故散点密集 → 点击该省，大屏全部图表切换为该省维度 → 在事故类型分布图中点击"追尾"类型，其余图表按该事故维度过滤 → 再选择车辆类型"货车"，流量与事故图表叠加货车维度过滤 → 大屏顶部标示当前生效的过滤条件组合 → 逐一解除过滤，恢复全国全量视图。

**场景 3：讲解时的数据冻结**
答辩讲解某图表细节时数据持续跳动影响讲解 → 开发者点击"暂停刷新"，全部图表与指标冻结在当前数值 → 静态讲解完成 → 点击"恢复刷新"，数据从冻结数值起连续恢复滚动。

**场景 4：多分辨率环境适配**
答辩现场投影设备分辨率为 1366×768（或 2560×1440），与 1920×1080 设计稿不一致 → 大屏自动等比缩放，内容完整呈现、无裁切与滚动条 → 演示过程中调整浏览器窗口大小，大屏实时重新适配。

**场景 5：管理员维护路网数据**
管理员打开登录页输入账号口令 → 登录成功后进入管理后台 → 在区域管理中新增一个城市并设置质心坐标 → 在路口管理中为该市新增路口 → 返回看板概览查看看板聚合数据 → 刷新大屏，新路口已出现在路口流量排行中（下一个数据刷新周期生效）。

**场景 6：全栈演示主流程**
开发者启动 MySQL、后端服务与前端 → 访客打开大屏，数据来自后端 SSE 推送 → 管理员登录后在后台展示路网维护与历史趋势 → 访客侧图表随推送平滑更新，展示"数据库 → API → 推送 → 可视化"的完整链路。

**场景 7：断网兜底演示**
演示现场无网络或数据库不可用 → 开发者以 `VITE_DATA_SOURCE=mock` 构建/启动前端 → 大屏由前端模拟引擎驱动，功能与全栈形态一致，答辩流程不受影响。

**场景 8：令牌过期与续期**
管理员登录后台并停留较长时间 → 访问令牌过期后再次发起请求 → 系统自动使用刷新令牌换取新访问令牌并重放该请求，管理员无感知 → 刷新令牌也已失效时，系统跳转登录页并要求重新登录。

## 3. 功能性需求

本章需求统一采用 EARS 句式描述：**当〔触发条件〕时，系统应当〔系统响应〕。**

### 3.1 地图可视化钻取

**FR-01｜全国地图初始加载｜P0｜迁移 → R-101**
当用户首次打开大屏页面且页面初始化完成时，系统应当默认呈现全国地图视图，以路况热力呈现各省拥堵程度强弱、以散点呈现各省事故分布，同时全部图表与 KPI 指标卡展示全国维度的汇总数据。

**FR-02｜省级地图下钻｜P0｜迁移 → R-102**
当用户在全国地图上点击某一省份区域时，系统应当将地图切换为该省的市级区划视图，并将路况热力与事故散点数据切换为该省下辖各地级市维度的数据，切换过程以过渡动画呈现。

**FR-03｜市级地图下钻｜P0｜迁移 → R-102**
当用户在省级地图上点击某一城市区域时，系统应当将地图切换为该市视图，展示该市范围内的路况热力与事故散点分布，且全部图表联动为该市维度（联动规则见 FR-06）；当目标城市地图数据不可用时，系统应当给出明确提示并保持当前视图与数据不变。

**FR-04｜逐级返回｜P0｜迁移 → R-102**
当用户处于省级或市级地图视图并触发"返回上一级"操作时，系统应当切换回上一级行政区划视图（市级 → 省级 → 全国），且大屏内全部图表与 KPI 指标同步回退至返回后层级维度的数据。

**FR-05｜地图区域悬浮提示｜P1｜迁移 → 沿用（交互细节，无独立 R 编号）**
当用户将鼠标指针悬浮于地图任一区域上时，系统应当显示包含该区域名称与核心运行指标（拥堵指数、在途车辆数、今日事故数）的悬浮提示框；当指针移出该区域时，系统应当立即隐藏提示框。

### 3.2 多图表联动

**FR-06｜地图区域选择联动｜P0｜迁移 → R-103**
当用户通过点击地图选定某一省或某一市时，系统应当将大屏内全部图表（KPI 指标卡、路口流量 TOP 排行、事故类型分布、车辆类型占比、拥堵指数趋势、24 小时分时流量热力）的展示数据自动切换为所选地区维度的数据，且各图表位置与布局保持不变。

**FR-07｜图表图例联动｜P0｜迁移 → R-103**
当用户点击任一图表的图例项或图形元素（如事故类型分布图的某一扇区、流量排行的某一柱项）时，系统应当以该图例所代表的业务维度作为全局过滤条件，自动刷新大屏内其他图表的数据；当用户取消选中该图例时，系统应当解除该维度过滤并恢复此前的展示状态。

**FR-08｜车辆类型过滤联动｜P0｜迁移 → R-103**
当用户选定某一车辆类型（如小汽车、公交车、货车、电动车）时，系统应当将流量、事故等所有关联图表按该车辆类型过滤刷新；当用户切换所选车辆类型时，系统应当按新类型重新过滤；当用户取消选择时，系统应当恢复全量车辆类型数据。

**FR-09｜联动过滤状态展示｜P1｜迁移 → R-103**
当任一全局过滤条件（地区、车辆类型、图表图例维度）生效时，系统应当在大屏的可见位置集中标示当前生效的全部过滤条件；当过滤条件发生变化或被解除时，系统应当实时更新该标示，全部条件解除后恢复默认（全国 / 全量）标示。

### 3.3 实时数据刷新

**FR-10｜周期性实时刷新｜P0｜迁移 → R-106**
当大屏处于运行状态且刷新未被暂停时，系统应当按设定的刷新周期（默认 5 秒）自动生成新一轮模拟数据，并刷新全部图表与 KPI 指标卡；相邻两轮数据应当保持数值连续、平滑过渡，不出现明显跳变。

**FR-11｜暂停 / 恢复刷新｜P0｜迁移 → R-106**
当用户点击"暂停刷新"控制时，系统应当立即停止周期性数据推送，将全部图表与 KPI 指标冻结在当前数值，并将控制状态明确标示为"已暂停"；当用户在暂停状态下点击"恢复刷新"控制时，系统应当立即恢复周期性数据推送，且恢复后的首批数据与冻结前数值保持连续。

**FR-12｜数据平滑过渡动画｜P1｜迁移 → R-106**
当任一图表接收到新数据或发生维度切换时，系统应当以平滑过渡动画呈现变化过程（数值渐变、柱高 / 弧度 / 散点位置渐变），动画期间图表布局不发生抖动、遮挡或错位。

### 3.4 KPI 指标卡

**FR-13｜KPI 指标卡展示｜P0｜迁移 → R-104**
当大屏加载完成时，系统应当在指标区展示四项核心 KPI：拥堵指数（附等级色标）、在途车辆数（辆）、今日事故数（起）、平均车速（km/h），四项指标均反映当前所选地区维度与过滤条件下的数值。

**FR-14｜KPI 实时更新｜P1｜迁移 → R-104**
当周期刷新推送新数据或全局过滤条件变化时，系统应当同步更新四项 KPI 指标卡的数值，更新过程即时呈现且不破坏指标卡布局。

### 3.5 专题图表展示

**FR-15｜路口流量 TOP 排行｜P0｜迁移 → R-105**
当大屏处于任一地区维度时，系统应当以排行榜形式展示该维度下路口流量 TOP N（默认前 10 名），包含路口名称与流量值（辆/时），按流量从高到低排列，并在每次刷新时更新排序与数值。

**FR-16｜事故类型分布｜P0｜迁移 → R-105**
当大屏处于任一地区维度时，系统应当以占比图形式展示该维度下各事故类型（追尾、刮擦、侧翻、碰撞行人、其他）的数量与占比，各类型占比合计为 100%，并在每次刷新时更新。

**FR-17｜车辆类型占比｜P0｜迁移 → R-105**
当大屏处于任一地区维度时，系统应当以环形占比图展示该维度下各车辆类型（小汽车、公交车、货车、电动车等）的在途车辆数量占比，各类型占比合计为 100%，并在每次刷新时更新。

**FR-18｜24 小时分时流量热力｜P0｜迁移 → R-105**
当大屏处于任一地区维度时，系统应当以热力图展示该维度下 24 小时分时流量强度分布（横轴覆盖 0 时至 23 时），以颜色梯度表征各时段流量强弱，整体呈现早高峰（7—9 时）与晚高峰（17—19 时）流量增强的分布特征，并在实时刷新时更新当前时段数据。

**FR-19｜拥堵指数趋势｜P1｜迁移 → R-105**
当大屏处于任一地区维度时，系统应当以趋势曲线展示该维度下拥堵指数随时间的变化走势（覆盖滚动时间窗口，不少于近 24 小时），并在每次刷新时追加最新数据点，曲线连续平滑。

### 3.6 大屏布局与显示控制

**FR-20｜大屏等比自适应缩放｜P0｜迁移 → R-107**
当浏览器窗口尺寸或显示分辨率与 1920×1080 设计基准不一致时，系统应当以等比缩放方式使大屏整体内容保持 16:9 比例完整呈现，不出现内容裁切、遮挡、错位或滚动条；当窗口尺寸发生变化时，系统应当实时重新计算并应用缩放比例。

**FR-21｜全屏模式切换｜P0｜迁移 → R-107**
当用户点击"全屏"控制时，系统应当进入浏览器全屏模式，并保持等比自适应缩放正常生效；当用户再次点击该控制、按下 ESC 键或浏览器退出全屏时，系统应当退出全屏并恢复常规窗口展示，布局保持正常。

## 4. 非功能性需求

### 4.1 性能

**NFR-01｜首屏加载时间｜P0**
当用户在满足运行环境要求的浏览器中首次打开大屏时，系统应当在 3 秒内完成首屏渲染（含全国地图、全部图表与 KPI 指标卡的首次呈现），本地开发环境与构建产物环境均应满足该指标。

**NFR-02｜图表过渡动画时长｜P1**
当任一图表发生数据刷新或维度切换动画时，单次过渡动画的时长应当不超过 500ms，保证演示节奏紧凑。

**NFR-03｜渲染帧率｜P0**
当大屏处于实时刷新、过渡动画与地图钻取的任一过程时，系统应当保持约 60fps 的稳定渲染帧率（单帧渲染耗时不超过 16.7ms），全程无可感知卡顿。

**NFR-04｜单次刷新开销｜P1**
当周期刷新触发全部图表重绘时，系统应当在不出现界面冻结的前提下完成重绘，单次重绘造成的主线程阻塞不超过 100ms。

### 4.2 兼容性

**NFR-05｜浏览器兼容｜P1**
系统应当在新版 Chrome 与新版 Edge 浏览器中完整运行，全部功能与视觉样式表现一致；不要求兼容 IE、旧版浏览器及移动端浏览器。

**NFR-06｜分辨率兼容｜P0**
当大屏运行于 2560×1440、1920×1080 或 1366×768 分辨率的显示环境时，系统应当以 1920×1080 为设计基准等比自适应，完整呈现全部内容且无布局破坏；其他 16:9 分辨率同样适用。

**NFR-07｜离线运行｜P0**
当运行环境完全断开网络时，系统应当保持全部功能正常可用：地图边界数据、模拟数据生成、图表渲染与全部交互均不依赖任何在线接口或在线资源，可完整支撑答辩演示全流程。

### 4.3 视觉规范

**NFR-08｜视觉风格｜P1**
大屏整体应当采用赛博朋克霓虹风格：深色底色，霓虹青、品红、紫渐变作为数据高亮主色调，关键视觉元素带辉光效果，界面模块采用圆角卡片设计；各图表数据系列在深色底上应当色彩可辨、对比清晰。

**NFR-09｜设计基准｜P1**
大屏应当以 1920×1080 设计稿为唯一布局基准，在任何目标分辨率下保持 16:9 等比缩放，文字字号、间距与图表尺寸随缩放比例等比变化，不出现元素错位。

### 4.4 可维护性

**NFR-10｜模块化结构｜P1**
系统代码应当按照功能模块组织（地图钻取、联动控制、模拟数据引擎、各图表组件相互分离），对单一图表或模块的调整不应当影响其他模块的功能。

**NFR-11｜刷新参数可配置｜P2**
刷新周期、数据波动幅度等运行参数应当以集中配置的方式管理，无需修改业务逻辑即可调整。

**NFR-12｜长时间运行稳定性｜P1**
当大屏连续运行不少于 2 小时（期间包含反复暂停/恢复、地图钻取与联动操作）时，系统应当保持帧率稳定、内存占用稳定，不出现卡顿加剧或浏览器崩溃。

### 4.5 服务端性能与可靠性（新增）

**NFR-13｜数据接口响应时间｜P0**
当客户端请求快照、看板聚合或历史趋势接口时，系统应当分别在 150ms（快照，取自内存态）、300ms（看板聚合）、500ms（历史趋势，单次不超过 2000 点）以内返回结果（P95，单机环境）。

**NFR-14｜服务可用性与故障恢复｜P1**
当后端遇到非法请求、数据库短暂不可用或推送连接异常时，系统应当保持进程存活、返回结构化错误而不崩溃；当数据库恢复或客户端网络恢复后，相关能力应当自动恢复（推送自动重连、查询自动重试一次）。

**NFR-15｜安全基线｜P0**
系统应当以加盐哈希方式保存管理员口令（不得明文或可逆加密），令牌使用对称签名算法且签名密钥长度不少于 32 字符，接口仅接受请求头中的 Bearer 令牌；响应与日志不得包含明文口令、口令哈希与签名密钥。

**NFR-16｜可观测性｜P1**
系统应当为每个请求生成请求标识并随响应头返回，错误日志记录请求标识、方法、路径与错误堆栈；采集任务应当记录最近运行时间、状态与消息，供运维与答辩演示查证。

**NFR-17｜部署与脚本一致性｜P0**
系统应当支持"前端与后端分别独立启动"的单机部署形态；数据库初始化脚本应当可重复执行（建表与种子数据幂等），连续执行两次不产生重复数据、不改变既有计数。

**NFR-18｜前后端可独立运行｜P1**
后端未启动时，前端管理后台应当给出明确错误提示而不白屏；前端未启动时，后端接口应当可被独立调用与验证。

## 5. 数据需求

### 5.1 数据来源与总体约束

系统数据来源分两档，二者产出同一结构的数据快照：

1. **默认来源（全栈形态）**：服务端采集器按周期生产模拟数据，经 API 与推送通道提供给前端；区域、路口等基础数据持久化在数据库中，由管理员维护。
2. **兜底来源（离线形态）**：前端内置模拟引擎按周期生成数据，不依赖后端、数据库与网络。

无论采用哪种来源，数据均具备以下总体特征：

1. **业务真实性**：数据符合城市交通的一般规律（早晚高峰、昼夜差异、拥堵与车速负相关），支撑演示可信度；
2. **数值连续性**：相邻刷新周期同一指标的变化幅度受平滑约束（不超过 ±15%），呈现连续波动而非随机跳变；
3. **维度完备性**：数据按全国、省、市三级地区维度组织，并可按车辆类型、事故类型等业务维度拆解与聚合，支撑联动过滤；
4. **口径一致性**：同一统计时刻，区域聚合值、类型明细与事故明细之间的求和关系必须闭合；
5. **演示自包含**：离线形态下全部模拟数据与地图边界数据随应用打包分发，运行时不发起任何在线请求。

### 5.3 数据质量约束

1. **数值连续性**：相邻两个刷新周期，同一地区、同一指标的数值变化幅度应当不超过 ±15%，禁止出现数量级跳变；
2. **日内规律**：24 小时分时流量应当呈现早高峰（7—9 时）与晚高峰（17—19 时）双峰分布，深夜（0—6 时）为全天低谷；
3. **拥堵指数分级**：0≤指数＜2 为畅通、2≤指数＜4 为基本畅通、4≤指数＜6 为轻度拥堵、6≤指数＜8 为中度拥堵、8≤指数≤10 为严重拥堵，KPI 指标卡色标与地图热力色标应当采用同一分级；
4. **指标相关性**：拥堵指数越高，平均车速应当越低（负相关）；在途车辆数高峰时段应当高于低谷时段；
5. **口径一致性**：同一统计时刻、同一地区口径下，KPI 指标卡展示的"今日事故数""在途车辆数"应当与对应明细实体（事故、车辆类型统计）的聚合结果一致；
6. **占比闭合**：事故类型占比合计为 100%，车辆类型占比合计为 100%；
7. **跨级闭合**：全部省份在途车辆之和与全国值相对误差小于 0.2%，全部车辆类型在途数之和与总量相对误差小于 0.1（全栈形态由后端保证，离线形态由前端引擎保证）；
8. **历史可回溯**：落库快照按固定粒度写入，历史趋势查询结果与写入粒度一致，缺失时段补零而不产生空洞错误；
9. **保留期约束**：区域快照保留 7 天、路口快照保留 3 天、分时流量与事故保留 90 天，超期数据自动清理，单日新增行数不超过 8 万行。

### 5.4 持久化数据实体（全栈形态新增）

全栈形态下系统维护 10 类业务数据实体，物理表结构、字段类型与索引设计见《技术设计文档》数据模型章节，数据库初始化脚本位于 `backend/sql/01_schema.sql` 与 `backend/sql/02_seed.sql`。

| 实体 | 业务含义 | 关键业务约束 |
| --- | --- | --- |
| 管理员账号（AdminUser） | 可登录管理后台的账号 | 用户名唯一；口令以加盐哈希存储；连续 5 次失败锁定 10 分钟；状态可禁用 |
| 刷新令牌（RefreshToken） | 管理员会话的续期凭据 | 仅存储摘要不可逆值；使用即轮换，旧凭据立即失效；可吊销、有到期时间 |
| 路网区域（Region） | 全国 / 省 / 市三级行政区划 | 编码唯一；层级固定三值；省归属全国、市归属省；被引用时不可删除；删除为逻辑删除 |
| 路口（Intersection） | 具体路口的流量观测点 | 编号唯一；必须归属已存在区域；权重大小影响流量基线；删除为逻辑删除 |
| 区域流量快照（RegionSnapshot） | 某一时刻区域的运行指标 | 同一区域同一时刻唯一；粒度 5 分钟；保留 7 天 |
| 路口流量快照（IntersectionSnapshot） | 某一时刻路口的流量与拥堵 | 同一路口同一时刻唯一；粒度 30 分钟；保留 3 天 |
| 分时流量（HourFlow） | 区域按小时汇总的流量 | 同一区域同一日期同一小时唯一；缺失小时补 0 |
| 事故记录（Accident） | 事故发生与处理记录 | 事故编号唯一；严重度与类型取值受枚举约束；处理中/已结案两态；保留 90 天 |
| 采集任务（CollectJob） | 采集器各子任务的运行状态 | 任务名唯一；记录最近运行时间、状态与消息 |
| 审计日志（AuditLog） | 管理写操作的留痕 | 记录操作者、动作、目标与时间；写入失败不影响业务结果 |

**种子数据规模（必须与计划一致）**：全国 1 条、省份 34 条、城市 66 条、路口 864 条、管理员 1 个、采集任务 5 条。
