# 答辩演示脚本（约 12 分钟）

## 开场白（30秒）

各位老师好，我是 XXX，我的毕业设计题目是《基于微服务架构的个人任务完成情况跟踪系统设计与实现》。下面我从研究背景、需求分析、系统设计、系统实现、系统测试五个方面进行汇报。

## 第一部分：研究背景（1分钟）

在快节奏的现代生活中，个人每天需要处理学习、工作、生活等多方面事务。现有的待办事项应用虽然功能丰富，但普遍存在两个问题：一是多采用单体架构，扩展性差；二是只记录"做什么"，缺乏对"完成得怎么样"的量化追踪。

微服务架构将系统拆分为多个独立部署的小服务，各服务拥有独立数据库，通过 API 通信。本课题以个人任务管理为场景，实践微服务架构的完整开发流程。

## 第二部分：需求分析（1.5分钟）

系统面向个人用户，包含四大功能模块：

第一，用户管理——注册、登录、JWT 鉴权、个人信息管理。密码要求至少8位且包含字母和数字。

第二，任务管理——任务的增删改查，支持分类、优先级、截止日期。任务状态按待办→进行中→已完成单向流转，允许从已完成重新打开为进行中。

第三，完成跟踪——每次任务完成自动记录完成事件，每次状态变更记录审计日志，用户可查看完成进度和完成率。

第四，统计报表——按日/周/月聚合完成数量，展示完成率趋势。

非功能需求方面，核心接口 P95 响应时间小于 200ms，所有接口经过参数校验，用户只能访问自己的数据。

## 第三部分：系统设计（3分钟）

系统拆分为四个微服务：

- user-service，端口 3001，负责用户注册登录和 JWT 签发，拥有 users 表。
- task-service，端口 3002，负责任务 CRUD 和状态流转，拥有 tasks 表和 outbox 表。
- tracking-service，端口 3003，负责完成事件记录和进度查询，拥有 completions 表和 status_logs 表。
- report-service，端口 3004，负责统计报表，不持久化数据，实时聚合下游接口。

技术栈选择 Node.js 18 + TypeScript + Express + SQLite。选择 SQLite 是因为它是嵌入式数据库，每个服务一个文件，无需独立部署数据库服务，适合毕设项目的规模。

这里我重点介绍两个关键设计：

**第一个是 Outbox 最终一致性方案。** 当 task-service 把任务标记为完成时，需要通知 tracking-service 记录完成事件。但如果 tracking-service 此时不可用怎么办？我们的方案是：在 task-service 的本地事务中，同时更新任务状态和写一条 outbox 记录，保证这两步原子性。事务提交后尝试调用 tracking-service，成功就删除 outbox 记录；失败就保留，由后台 Worker 每 30 秒扫描重试，最多 5 次，指数退避。这样主流程不会被下游故障阻塞，数据最终一致。

**第二个是游标分页。** 传统的 OFFSET 分页在数据变动时会错位，而且大偏移量性能差。我们用 base64 编码的游标记录上一页最后一条记录的创建时间，查询时用 WHERE created_at < ? 条件，和 GitHub API 的方案一致。

## 第四部分：系统实现（3分钟）

下面演示核心调用链路。

（演示 curl 命令）

第一步，注册用户：POST /api/users/register，传入用户名、邮箱、密码。注册成功返回 userId。

第二步，登录：POST /api/users/login，返回 JWT Token。

第三步，创建任务：携带 Token，POST /api/tasks，传入标题和优先级。任务初始状态为 TODO。

第四步，标记完成：PATCH /api/tasks/:id/status，状态改为 DONE。此时 task-service 会通知 tracking-service 记录完成事件。

第五步，查询进度：GET /api/tracking/progress，返回待办数、进行中数、已完成数和完成率。

第六步，查询报表：GET /api/reports/summary，传入时间范围，返回完成汇总。

安全方面，密码使用 bcrypt 不可逆加密存储；所有受保护接口校验 JWT；服务间调用通过 X-Internal-Token 信任；查询接口在 SQL 层面强制按 user_id 过滤，从根本上防止越权。

部署方面，每个服务有独立 Dockerfile，通过 docker-compose 一键启动全部 4 个服务。

## 第五部分：系统测试（1.5分钟）

功能测试覆盖了注册登录、任务 CRUD、状态流转、进度查询和报表接口，全部通过。

安全性测试验证了：密码加密存储、无 Token 访问被拒绝、越权访问他人任务返回 404、内部接口需要 X-Internal-Token。

容错测试：我手动停止 tracking-service 后标记任务完成，接口仍然返回成功；恢复 tracking-service 后，outbox Worker 自动补录了完成事件，验证了最终一致性方案的有效性。

## 总结（1.5分钟）

总结一下，本系统完成了：4 个微服务的完整实现、用户鉴权与任务状态机、Outbox 最终一致性补偿、游标分页、Docker 一键部署。

不足之处在于：目前只有后端 API，没有前端界面；使用 SQLite 在高并发场景下能力有限；没有引入服务注册中心和链路追踪。

未来可以：开发前端管理界面、将 SQLite 替换为 PostgreSQL、引入消息队列替代同步调用、增加数据可视化图表。
