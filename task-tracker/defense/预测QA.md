# 答辩预测 Q&A（20题）

## 一、架构设计类

**Q1：为什么在个人任务管理这种小型场景下要用微服务？是不是过度设计？**
A：这是一个好问题。确实，个人任务管理的业务规模用单体架构完全可以胜任。本课题的目的是教学实践——通过完整实现 4 个微服务，掌握微服务拆分、独立数据库、跨服务通信、最终一致性、容器化部署等核心技术。在实际生产中，如果团队规模小、业务简单，单体架构确实更合适。但微服务架构的优势在于当业务增长时可以独立扩展某个服务，且各服务技术栈可以异构。

**Q2：为什么选择 SQLite 而不是 MySQL/PostgreSQL？**
A：主要考虑三点：第一，SQLite 是嵌入式数据库，每个服务一个文件，无需独立部署数据库服务，符合微服务"独立数据库"原则的同时降低了运维成本；第二，better-sqlite3 提供同步 API，事务处理代码更简洁；第三，毕设演示场景数据量小（预计<10万行），SQLite 性能完全足够。生产环境可以平滑替换为 PostgreSQL。

**Q3：为什么不引入 API 网关？**
A：系统只有 4 个服务，且各服务都实现了统一的 JWT 鉴权中间件，客户端可以直接访问各服务端口。引入 API 网关（如 Kong、Nginx）会增加部署复杂度。在服务数量增长后，可以在前面加一层 Nginx 反向代理统一入口。

**Q4：服务发现为什么用配置式而不是 Consul/Eureka？**
A：配置式服务发现（环境变量注入服务地址）在 4 个服务的规模下足够简单可靠。引入 Consul 或 Eureka 会增加额外的中间件运维成本。Docker Compose 网络内可以直接通过服务名解析，天然提供了服务发现能力。

## 二、数据一致性类

**Q5：Outbox 模式和 Saga 模式有什么区别？**
A：Saga 模式强调跨服务事务的编排，每个步骤成功后执行下一步，失败时执行补偿事务，适用于长流程业务。Outbox 模式更简单——它利用本地事务保证"业务数据变更"和"事件写入"的原子性，然后异步投递事件，适用于"通知型"场景。本系统中任务状态更新和事件记录是"主从"关系而非"编排"关系，Outbox 模式更合适。

**Q6：如果 outbox 重试 5 次都失败了怎么办？**
A：记录会标记为 FAILED 状态，保留在 outbox 表中。当前实现只是简单告警。生产环境可以接入监控系统（如 Prometheus + AlertManager），当 FAILED 记录数超过阈值时通知运维人员介入。也可以增加死信队列和人工重试界面。

**Q7：为什么不用消息队列（RabbitMQ/Kafka）替代 Outbox？**
A：消息队列确实是更标准的事件驱动方案，可以提供持久化、投递保证和消费者组。但引入消息队列需要额外部署和维护中间件。Outbox 模式利用本地数据库实现了轻量级的可靠事件投递，在本系统规模下足够。如果未来事件量增大或需要多个消费者，可以平滑迁移到消息队列。

## 三、技术细节类

**Q8：JWT 的有效期为什么设为 7 天？会不会太长？**
A：7 天是一种权衡。有效期短更安全（Token 被盗后影响窗口小），但用户需要频繁登录。7 天在安全性和体验之间取得平衡。生产环境可以配合 Refresh Token 机制——Access Token 有效期短（如 15 分钟），Refresh Token 有效期长（如 7 天），提升安全性。

**Q9：bcrypt 的 cost factor 为什么选 10？**
A：cost factor 每增加 1，哈希时间翻倍。cost=10 时单次哈希约 100ms，在安全性（暴力破解成本）和用户体验（登录等待时间）之间取得平衡。更高的 cost（如 12）更安全但登录等待更长。

**Q10：游标分页的游标为什么用 base64 编码？直接传 JSON 字符串不行吗？**
A：base64 编码有两个好处：一是 URL 安全（base64url 不含 +/= 等需要 URL 编码的字符）；二是防止用户随意篡改游标参数。虽然 base64 不是加密，但增加了直接修改 sortValue 的门槛。生产环境可以对游标进行 HMAC 签名，防止篡改。

**Q11：为什么 report-service 不持久化统计结果？**
A：spec 明确要求 report-service 的数据来源于 tracking-service 的实时聚合，不维护数据副本，以避免数据不一致。如果性能成为瓶颈（数据量大时聚合慢），可以在 report-service 中引入 Redis 缓存，设置合理的过期时间。

**Q12：系统怎么防止 SQL 注入？**
A：所有数据库查询都使用 better-sqlite3 的 prepared statements（预编译语句），参数通过占位符绑定，不拼接 SQL 字符串。同时所有用户输入经过 zod schema 校验，从两个层面防止 SQL 注入。

## 四、业务逻辑类

**Q13：为什么任务状态不允许 DONE 直接回退到 TODO？**
A：这是业务设计决策。从已完成直接回到待办意味着任务从未开始过，不符合用户的心智模型——用户完成过的任务应该有历史记录。如果用户想重新开始一个已完成的任务，应该"重新打开"为进行中（DONE→IN_PROGRESS），这样既保留了完成历史，又允许继续操作。

**Q14：完成率是怎么计算的？分母是什么？**
A：完成率 = 已完成数 / (待办数 + 进行中数 + 已完成数)。分母为 0 时返回 0。这里"已完成数"取 task-service 中 status=DONE 的任务计数，而不是 tracking-service 中的完成事件数——因为一个任务可能被多次完成（重新打开后再完成），用任务计数更准确。

**Q15：用户删除任务后，完成历史和状态日志会怎样？**
A：完成事件和状态日志保留在 tracking-service 中，通过 taskId 软关联。这样做是为了审计追溯——即使任务被删除，用户的完成统计仍然保留历史记录。这也是为什么 tracking-service 的表中有 task_id 但没有外键约束。

## 五、测试与部署类

**Q16：测试覆盖率达到了多少？**
A：按照设计要求，单元测试覆盖率目标为 ≥70%。测试覆盖了 Repository 层的 CRUD 与边界条件、Service 层的业务逻辑（注册重复、密码复杂度、状态机合法/非法流转、越权校验）、以及 HTTP 集成测试（supertest 覆盖全链路）。

**Q17：docker-compose up 之后怎么验证系统正常工作？**
A：首先检查 4 个服务的 healthcheck 状态是否为 healthy。然后按照 README 中的 curl 示例依次执行注册→登录→创建任务→标记完成→查询进度→查询报表，每一步都应返回 code=0。

**Q18：如果要部署到云服务器，需要做什么调整？**
A：主要调整：第一，JWT_SECRET 和 INTERNAL_TOKEN 替换为强随机值；第二，SQLite 替换为 PostgreSQL（各服务连接字符串改为环境变量）；第三，在前面加 Nginx 反向代理配置 HTTPS；第四，配置进程管理（如 PM2 或 Kubernetes）保证服务异常自动重启；第五，配置集中式日志（如 ELK）和监控告警。

## 六、总结反思类

**Q19：做这个毕设最大的收获是什么？**
A：最大的收获是理解了微服务架构不是简单地把单体拆成几个服务——真正的挑战在于跨服务数据一致性、服务间容错、分布式鉴权这些"非业务"问题。特别是 Outbox 模式，让我理解了为什么本地事务 + 异步补偿在很多场景下比分布式事务更实用。

**Q20：这个系统还有什么可以改进的地方？**
A：主要有四个方向：第一，开发前端界面（目前只有 API），用 React/Vue 做任务管理和数据可视化；第二，引入消息队列解耦服务间调用；第三，增加 WebSocket 实现实时通知；第四，引入分布式链路追踪（如 OpenTelemetry）排查跨服务问题。这些受限于毕设时间没有实现，但都是后续可以探索的方向。
