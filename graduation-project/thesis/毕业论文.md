## 摘 要

随着城市机动车保有量持续增长，交通管理部门对运行态势的实时感知与集中研判提出了更高要求，数据可视化大屏已成为交通指挥中心的核心信息载体。然而，传统大屏普遍依赖后端数据服务与在线地图资源，部署链路长、离线可用性差，难以在无网络环境下支撑演示与教学。针对上述问题，本文设计并实现了一个面向交通指挥监控场景的纯前端城市交通监控可视化大屏。系统基于 Vue 3.5 组合式 API 与 TypeScript 5.8 严格模式构建，采用 Vite 6 进行构建，以 Pinia 2 作为单一数据源（SSOT）状态容器，通过 ECharts 5.6 按需渲染六类图表，实现了三大核心能力：其一，基于 geoJSON 动态注册的全国—省—市三级地图钻取；其二，以单一数据源为枢纽的地区、车辆类型、事故类型三维度全图表联动过滤；其三，以双正弦波与有界随机游走构成的平滑噪声模型驱动的 5 秒周期实时数据刷新，配合 60 倍加速的模拟时钟呈现完整日内规律。系统内置纯前端模拟数据引擎，生成 34 个省级行政区、66 个城市与 864 个路口的连续演化数据，全部地图边界数据本地打包为异步分片，断网环境可完整运行。测试结果表明：相邻数据快照最大变化率为 2.37%（约束阈值为 15%），早高峰流量为深夜低谷的 5.9 倍，聚合口径闭合误差小于 0.2%，首屏 gzip 资源总量约 470 KB 并可在 3 秒内完成渲染；6 项自动化数据质量测试全部通过。本系统为交通态势可视化的教学演示与同类大屏工程提供了完整、可复用的纯前端技术方案。

## Abstract

With the continuous growth of urban vehicle ownership, traffic management authorities have raised higher requirements for real-time perception and centralized analysis of traffic conditions, and data visualization dashboards have become the core information carrier of traffic command centers. However, traditional dashboards generally rely on backend data services and online map resources, which results in long deployment chains and poor offline availability. To address these problems, this thesis designs and implements a purely front-end urban traffic monitoring visualization dashboard for traffic command and monitoring scenarios. The system is built on Vue 3.5 with the Composition API and TypeScript 5.8 strict mode, bundled by Vite 6, with Pinia 2 as the Single Source of Truth (SSOT) state container, and renders six types of charts on demand through ECharts 5.6. Three core capabilities are realized: first, three-level map drilling from country to province to city based on dynamic geoJSON registration; second, three-dimensional chart linkage filtering (region, vehicle type, accident type) centered on the SSOT; third, real-time data refreshing on a 5-second cycle driven by a smooth noise model composed of dual sinusoidal waves and a bounded random walk, together with a 60-times accelerated simulated clock presenting complete intra-day patterns. The system embeds a purely front-end simulation engine that generates continuously evolving data for 34 provincial regions, 66 cities and 864 intersections; all map boundary data are packaged locally as asynchronous chunks so that the system can run completely offline. Test results show that the maximum change rate between adjacent snapshots is 2.37% (threshold 15%), the morning peak flow is 5.9 times the midnight valley, the aggregation consistency error is below 0.2%, and the total first-screen gzip payload is about 470 KB with rendering completed within 3 seconds; all six automated data quality tests pass. The system provides a complete and reusable purely front-end solution for traffic situation visualization demonstration and similar dashboard engineering.

**Keywords:** data visualization; traffic monitoring; Vue 3; ECharts; single-page application; simulation data engine

## 第一章 绪论

### 1.1 研究背景与意义

近年来，我国城镇化进程持续推进，城市机动车保有量逐年攀升，交通拥堵、交通事故等城市运行问题日益突出，给交通管理部门的态势感知与应急响应能力带来了严峻挑战。传统的交通管理方式以表格报表与离散监控画面为主，信息分散、时效性差，难以支撑指挥中心对全局态势的集中研判。在此背景下，智慧交通系统通过汇集卡口、地磁、浮动车等多源感知数据，为交通管理提供了丰富的数据基础，但原始数据本身并不具备直接的可读性，必须借助可视化手段才能转化为可感知、可研判的态势信息。

数据可视化大屏是解决上述问题的重要载体。大屏以地理空间分布为骨架，将路况热力、事故分布、核心运行指标、流量排行、分时规律等多维信息组织在同一视野内，使值守人员能够在数秒内完成"总览—定位—下钻—联动"的研判闭环，其信息密度与决策支撑能力远超传统报表。在交通指挥中心、节假日保障、重大活动安保等场景中，可视化大屏已成为标准配置，相关设计与实现技术也构成了工业界与学术界共同关注的方向。

然而，现有大屏系统普遍采用"前端展示 + 后端服务 + 数据库"的架构形态，地图边界数据亦多依赖在线地图服务。此类方案在生产环境下是合理的选择，但在教学演示、毕业答辩、方案汇报等场景中却暴露出明显不足：部署链路长、环境依赖重、断网不可用、演示风险高。与此同时，大屏所依赖的核心前端技术——组件化框架、状态管理、地理可视化与数据模拟——恰恰是前端工程能力训练的完整闭环。因此，本文选取"城市交通监控可视化大屏"为题，采用纯前端技术路线：以内置于前端的模拟数据引擎替代后端数据服务，以本地打包的 geoJSON 替代在线地图资源，实现一块断网可完整运行、三大交互亮点突出、工程实践完整的监控大屏。该选题既具有明确的业务应用背景，也具备扎实的工程技术训练价值。

### 1.2 国内外研究现状

#### 1.2.1 数据可视化与大屏技术的发展

数据可视化的理论研究由来已久。Tufte 系统阐述了图形设计的量化原则，奠定了现代统计图表设计的理论基础[10]；Shneiderman 提出了"先总览、再缩放过滤、后按需细节"（Overview first, zoom and filter, details on demand）的信息可视化交互箴言，至今仍是可视化系统交互设计的通用准则[9]；Ware 从感知心理学角度论述了颜色、形状与空间编码的有效性，为可视化视觉通道选择提供了实证依据[11]；Munzner 进一步提出了嵌套的数据—任务—有效编码分析框架，使可视化设计决策有章可循[8]。在仪表盘（Dashboard）设计方向，Few 对大屏与仪表盘的常见误区与最佳实践进行了系统总结[12]，Wilkinson 则从图形语法的高度对统计图表进行了形式化描述[13]。

在 Web 可视化工具层面，技术形态经历了从命令式图形库到声明式框架的演进。早期以 Prefuse、Flare 为代表的 Java/Flash 工具受限于运行环境；D3.js 以数据驱动文档的思想确立了命令式可视化编程范式[6]，灵活性极强但开发成本较高；以 ECharts、Chart.js、Highcharts 为代表的声明式框架则通过"配置即图表"的方式大幅降低了开发门槛。ECharts 由百度前端技术部开源并捐赠至 Apache 软件基金会，其声明式框架设计经学术界系统论述[5]，凭借 Canvas 渲染性能、丰富的图表类型与 geoJSON 地图注册机制，已成为国内数据可视化领域应用最广泛的开源库之一，也是政务、交通、金融等行业大屏的主流选择。

#### 1.2.2 Web 前端技术的演进

Web 前端技术在过去十余年间经历了深刻变革。框架层面，从以 DOM 操作为中心的 jQuery 模式演进为以数据绑定为核心的 MVVM 模式，Vue.js 以渐进式、低心智负担的特点成为国内应用最广的视图框架之一[18]；Vue 3 引入基于 Proxy 的响应式系统与组合式 API，将逻辑组织从"选项分类"转变为"功能聚合"，显著提升了复杂组件与逻辑复用的工程化水平，其设计原理已被系统梳理成著[2][3]。状态管理层面，Vuex 向 Pinia 的演进简化了样板代码并完整支持组合式 API。构建工具层面，从 Grunt/Gulp 的任务流模式，到 Webpack 的模块打包模式，再到 Vite 基于浏览器原生 ES Module 与 esbuild 预构建的按需编译模式，开发体验与构建效率均有数量级的改善。语言层面，TypeScript 以静态类型系统为大型前端工程提供了类型安全与契约显式化的能力[4]，已成为主流工程标配[17]。上述技术共同构成了本系统实现的技术底座。

#### 1.2.3 智慧交通可视化应用现状

在应用层面，智慧交通可视化已在行业内广泛落地。各地交警指挥中心普遍建设了以地图为核心的一体化态势大屏，集成信号控制、事件接报、流量监测等业务数据；互联网地图厂商则面向公众提供实时路况服务。学术界围绕交通流仿真、交通状态评估等方向开展了大量研究，杨兆升等系统论述了智能交通系统的体系结构[14]，交通工程学对交通流的统计规律（如早晚双峰的日变化特性）已有成熟结论[15]，为交通数据的模拟生成提供了理论依据。综观现状，行业大屏实现方案以"前后端分离 + 在线地图服务"为主，对纯前端离线场景下的大屏工程化实践（本地地图资源、数据模拟引擎、纯前端联动架构）的系统论述相对有限，这正是本文工作的切入点。

## 第二章 相关技术介绍

### 2.1 Vue 3 响应式与组合式 API

Vue 是一款用于构建用户界面的渐进式 JavaScript 框架，其核心是响应式数据驱动视图的更新机制。Vue 3 以 ES6 Proxy 重写了响应式系统：当组件读取响应式状态时自动收集依赖，状态变更时精确触发依赖更新，从而实现数据到视图的自动同步。相较于 Vue 2 基于 Object.defineProperty 的实现，Proxy 能够拦截对象属性的新增、删除以及数组索引的直接赋值，规避了历史版本中已知的响应式盲区，同时也带来了更优的初始化性能。

组合式 API（Composition API）是 Vue 3 的标志性特性。它允许开发者以 `ref`、`computed`、`watch` 等响应式原语按"功能内聚"的方式组织代码，将同一业务逻辑所需的状态与副作用聚合在一起，解决了选项式 API（Options API）在复杂组件中逻辑分散、复用困难的问题。逻辑复用层面，组合式函数（composables）取代了 mixin，具有来源清晰、无命名冲突、类型推断完整等优点。本系统将 ECharts 实例生命周期托管与屏幕等比缩放分别封装为 `useECharts` 与 `useScreenAdapter` 两个组合式函数，正是对这一能力的典型运用。

此外，Vue 3 提供了单文件组件（SFC）、异步组件、`shallowRef` 浅层响应式等工程化能力。其中 `shallowRef` 仅追踪引用本身的变化而放弃深层属性追踪，对于以"整体替换"方式更新的大型数据快照（如本系统的数据快照对象）而言，可显著降低响应式代理开销。

### 2.2 ECharts 可视化原理

ECharts 是一个基于 JavaScript 的声明式可视化框架，其整体架构由上层的语义层与下层的渲染层 zrender 构成[5]。语义层将开发者声明的 `option` 配置解析为坐标系、组件与系列（series）的内部模型；渲染层通过 Canvas 或 SVG 渲染器将模型绘制为位图或矢量图形。Canvas 渲染器以整块画布承载全部图元，在数千级图元规模下依然保持流畅的重绘性能，是大屏类应用的首选。ECharts 的增量渲染与过渡动画机制使得数据更新时仅变化部分参与重绘，且柱高、弧度、散点位置等属性以插值动画平滑过渡，这为本系统的实时刷新提供了直接支撑。

地理可视化方面，ECharts 自 5.0 起不再内置中国地图，而是提供 `registerMap` 接口由开发者自行注册 geoJSON 边界数据。geoJSON 是描述地理要素的开放标准格式，其 `features` 数组中每个要素的 `properties` 携带区域名称与行政区编码（adcode），`geometry` 则以多边形坐标串描述边界。注册后的地图可与 `visualMap` 视觉映射组件配合：`visualMap` 将数据值域映射为颜色梯度，叠加在地图 series 上即形成表示区域指标强弱的热力分层图（choropleth）；`effectScatter`（涟漪特效散点图）则可在同一坐标系上叠加带涟漪动画的点位标记，适合表达事件的空间分布。上述机制共同构成本系统地图钻取与路况呈现的技术基础。

工程化方面，ECharts 支持按需引入：开发者通过 `echarts/core` 的 `use` 方法显式注册所需的图表类型、组件与渲染器，未注册的部分可被构建工具从产物中摇除（tree-shaking），从而显著削减打包体积。

### 2.3 Pinia 状态管理

Pinia 是 Vue 官方推荐的状态管理库，可视为 Vuex 的继任者。相较于 Vuex，Pinia 移除了 mutation 环节，允许在 store 中直接执行异步与同步逻辑；其 store 以扁平结构组织，天然支持代码分割与按需引入，并在 TypeScript 环境下提供完整的类型推断，无需手写类型注解。

Pinia 提供选项式与组合式（Setup Store）两种定义方式。组合式 store 以普通函数形式定义，内部使用 `ref`/`computed` 声明状态与派生数据，与组件内的组合式 API 写法保持一致，语义直观。本系统采用组合式语法定义唯一的大屏 store：原始数据快照以 `shallowRef` 存放，钻取栈与过滤维度以 `ref` 存放，各图表消费的视图数据一律由 `computed` getters 派生。当任意过滤维度变化时，相关 getters 自动重算并驱动订阅组件更新，这正是实现多图表联动的核心机制。

Pinia 的单 store 承载全局唯一业务数据与过滤状态的用法，本质上是在前端落地了"单一数据源"（Single Source of Truth，SSOT）原则：任何视图数据都只有一份权威来源与确定性派生路径，不存在第二份副本，从机制上保证了各图表展示口径的一致性。

### 2.4 Vite 构建工具与 ES Module

Vite 是新一代前端构建工具，其开发环境利用浏览器原生 ES Module 实现"按需编译"：模块在浏览器请求时才被转换，配合 esbuild 对依赖的预构建，冷启动与热更新速度较传统打包器有数量级提升。生产构建则基于 Rollup 完成模块打包与优化，支持代码分割（code splitting）：入口依赖构成同步 chunk，动态 `import()` 的模块则拆分为异步 chunk，在首次访问时才加载。

Vite 对 JSON 模块与资源内联策略的处理与本项目直接相关：超过内联阈值的 JSON 资源会自动外置为独立异步 chunk，结合 `import.meta.glob` 通配导入机制，可将一组静态资源映射为"路径 → 懒加载函数"的字典，实现资源的按需懒加载。本系统 9 份 geoJSON 边界数据即以此方式打包为异步分片：首屏仅加载全国边界，省市边界在下钻瞬间才按需获取，在保证断网可用的同时控制了首屏体积。

### 2.5 TypeScript

TypeScript 在 JavaScript 语法之上叠加了静态类型系统，包括接口、泛型、联合类型、字面量类型与类型收窄等能力，可在编译期拦截大量低级错误[4][17]。开启严格模式后，空值检查与隐式 any 等高风险写法将被禁止，类型约束的完整性与可信度进一步提升。

类型系统在前端工程中的价值不仅是纠错，更在于"契约显式化"：领域实体、组件 Props、store 返回值等跨模块边界的数据形状均以类型声明固化，模块间的依赖关系因此具备可推导性与自文档性。本系统以 TypeScript 5.8 严格模式编写全部业务代码：数据引擎的实体与快照结构、12 个组件的 Props 契约、store 的 getters 返回类型均以显式接口约束，重构与联调成本显著降低。

### 2.6 数据可视化设计理论

可视化设计理论为本系统的视觉方案提供了依据。格式塔知觉理论指出，人眼倾向于将邻近的元素视为一组、将相似的元素归为一类、将间断的线段知觉为连续整体。据此，本系统将大屏内容组织为边界清晰的圆角卡片群：同一卡片内的标题、图表与辅助信息因接近性而成组，卡片间以统一间距分隔，用户无需阅读文字即可完成视觉分区。

色彩语义层面，深色底大屏已成为指挥中心场景的主流形态：深色背景降低环境光反射与视觉疲劳，同时使高饱和度的数据色获得最大对比度[11]。色带的选择需同时满足"序"与"义"两方面要求：对拥堵指数这类有序变量，采用从绿灯色系到红灯色系的单射渐变色带，使"越红越堵"成为无需学习的语义映射；对分类变量（事故类型、车辆类型），则选用色相差异显著的多色板并限制类别数量，避免色彩混淆。Shneiderman 的可视化交互箴言[9]进一步指导了本系统的交互设计：地图缩放对应"缩放与过滤"，全国—省—市钻取对应"按需细节"，而全图表联动则将"过滤"升维至全局语义，使任一维度的选择同步作用于整块大屏。

## 第三章 系统需求分析

### 3.1 系统概述

本系统面向交通管理指挥中心的监控场景，以一块沉浸式数据大屏集中呈现城市交通运行态势：地图路况热力与事故分布、核心运行指标、路口流量排行、事故构成、车辆结构与分时流量规律一屏尽览。系统采用纯前端技术路线，不依赖任何自建后端服务，全部数据由前端内置的模拟数据引擎离线生成，因此可在完全断网的环境下完整演示。系统的用户角色设定为三类：交通指挥中心值班员（演示目标用户）、答辩评委（评审者）与开发者（毕业生本人）。系统无账号体系，所有角色均以普通访客身份直接使用大屏，无权限差异。

### 4.1 总体架构设计

系统采用五层单向依赖架构，自底向上依次为资源层（L1）、数据引擎层（L2）、状态层（L3）、组合函数层（L4）与视图层（L5），如图 4-1 所示。

**图 4-1 系统五层总体架构**

分层职责与依赖规则如下：其一，单向依赖，L5 → L4 → L3 → L2 → L1 严格单向，禁止反向依赖；数据引擎层不感知任何框架 API，从而可脱离浏览器环境独立运行单元测试，这是模块化非功能需求在架构层面的落点。其二，单一数据源，全部业务数据（当前快照、过滤状态、钻取层级）只存在于状态层的唯一 store 中；图表组件是无业务状态的"渲染器"，仅接收派生数据。其三，事件收敛，地图点击、扇区点击、图例点击等全部联动入口统一由视图层转发至 store action，图表之间互不感知，杜绝组件网状通信。其四，失败兜底，地图数据缺失、下钻不可用等异常一律经由 store 的全局提示状态驱动界面提示，组件自身不处理弹窗逻辑。

### 4.3 路由设计

系统采用 Vue Router 4 的 hash 模式，路由表仅两条：主路由 `/` 对应大屏视图 ScreenView，首屏同步加载；辅助路由 `/about` 对应系统说明页 AboutView，采用动态 `import()` 懒加载，承载技术栈、三大亮点原理与架构分层的答辩讲解内容，不参与业务数据流。

选择 hash 模式的决策依据在于离线分发约束：hash 路由的 URL 以 `#` 携带路径，浏览器不会向服务器发起路由请求，构建产物无论以静态服务器还是本地文件方式打开均可正确路由；而 history 模式在静态托管下需要服务器配置 fallback 重写规则，属于不必要的部署风险。路由级生命周期另有约定：ScreenView 挂载时启动数据引擎，离开路由时必须停止引擎并触发全部图表销毁，以防止内存泄漏。

### 4.4 数据流与联动机制设计

#### 4.4.1 单一数据源（SSOT）原则

联动机制的设计基石是 SSOT 原则，具体包含四层含义：唯一事实数据——数据引擎每个周期产出的全量快照，整体写入 store；唯一过滤状态——地区钻取栈与两个类型维度选择，全部存放于 store；唯一派生口径——所有图表消费的视图数据一律由 getters 计算，图表组件与视图层禁止自行过滤或聚合；组件本地仅允许存放界面态（悬浮、动画中间量），凡出现业务数据第二份副本即视为设计违例。该原则将"口径一致性"从人工约定提升为架构强制。

#### 4.4.2 实时刷新链路

实时刷新的数据流如图 4-2 所示。

```

    ▼

    │ Vue 响应式批处理（同一微任务内合帧）

```

暂停/恢复的连续性设计是本链路的关键点：暂停并非简单地清除定时器并让内部时钟空转，而是同时冻结引擎的模拟时钟。由于噪声模型的正弦相位与随机游走项均以模拟时间为自变量，时钟冻结即全部相位冻结，恢复时从冻结点无缝续推，因此"恢复后首批数据与冻结前数值连续"由构造保证，无需任何补偿逻辑。

### 4.5 模拟数据引擎设计

模拟数据引擎是本系统区别于常规可视化工程的核心设计，目标是离线生成"看起来真实"的连续数据流。引擎由常量、实体工厂、噪声模型、聚合与调度五个模块组成，无任何框架依赖。

#### 4.5.1 实体体系与权重链

引擎生成 34 个省级行政区、66 个城市（覆盖 4 个内置省份的全部地级市）与 864 个路口实体。数值生成采用层级基准链：全局在途车辆基准（320 万辆）乘以省份权重再乘以城市占省比，得到各城市的基准量级；非内置省份因无城市明细，直接按省权重生成省级实体，仅服务全国视图热力，不参与下钻。省份权重取值范围 0.30~1.00（广东最高为 1.00），城市占省比按"省会约 0.30、副中心约 0.12、普通地市 0.03~0.08"设定并归一。车辆类型结构占比基准为：小汽车 62%、电动车 17%、货车 13%、公交车 8%，叠加 ±3 个百分点的地区微扰后归一，保证各类型占比合计恒为 100%。

#### 4.5.2 平滑噪声模型

数值连续性由平滑噪声模型保证。对每个指标通道，取时刻 t 的原始值为：

```text
raw(t) = base × weight(region) × hourFactor(h(t))
       × ( 1 + A₁·sin(2πt/T₁ + φ₁) + A₂·sin(2πt/T₂ + φ₂) ) + w(t)     …（4-1）
```

式中 base 为该指标基准值，weight 为区域权重，hourFactor 为时段因子（见式 4-2）；双正弦项中 T₁ = 300 s（慢波）、T₂ = 40 s（快波），振幅 A₁ = 0.10、A₂ = 0.05，初相位 φ₁、φ₂ 由随机数生成，使各通道波形彼此独立。w(t) 为有界随机游走项：

```text
w(t) = clamp( w(t−Δ) + σ·N(0,1),  −W_max, +W_max )                     …（4-2）
       其中 W_max = 8% × base，σ = 1% × base
```

即每步叠加一个零均值正态扰动（Box–Muller 变换产生 N(0,1)），但累计漂移被硬性限制在基准值的 ±8% 以内，既提供不可预测性，又排除长期趋势漂移。输出前施加两道钳制构成"双重闸门"：先做连续性钳制，将本时刻输出限制在上一时刻值的 0.85~1.15 倍区间内（对应 ±15% 的数据质量约束）；再做业务值域钳制，将结果限制在指标定义域内（如拥堵指数 [0,10]、平均车速 [15,80] km/h）：

```text
value(t) = clamp( raw(t),  0.85 × value(t−Δ),  1.15 × value(t−Δ) )     …（4-3）
value(t) = clamp( value(t),  min,  max )                               …（4-4）
```

设计意图可概括为：双正弦波提供"有节奏的呼吸感"，随机游走提供"观测噪声的真实感"，双重钳制则从数学上排除数量级跳变的可能。由于全部项均以模拟时间为自变量，时钟冻结即相位冻结，这直接支撑了暂停恢复的连续性。

#### 4.5.3 早晚双峰时段因子

日内规律由时段因子 hourFactor 刻画。以 G(h; μ, σ) 表示以 μ 为中心、σ 为标准差的高斯核：

```text
G(h; μ, σ) = exp( −(h−μ)² / (2σ²) )                                   …（4-5）

hourFactor(h) = 0.16                          # 深夜低谷基线
              + 0.62 · G(h; 8.0, 1.3)         # 早高峰（7—9 时，峰值约 0.78）
              + 0.78 · G(h; 18.0, 1.6)        # 晚高峰（17—19 时，峰值约 0.94）
              + 0.30 · bump(h)                # 日间平台（10—16 时）

bump(h) = sin(π·(h−10)/7)，当 h∈[10,16]；否则 0                     …（4-6）
```

该函数满足交通工程学对城市交通流日变化的一般结论[15]：深夜（0—6 时）处于全天低谷；通勤驱动的早晚双峰形态明显，且晚高峰（叠加日间出行惯性）略高于早高峰；曲线处处光滑、无台阶。进一步地，四类车辆类型采用差异化时段形状以增强联动过滤后的可视差异：小汽车使用标准形状；公交车双峰更尖（σ 收窄至 1.0）；货车呈现 8—17 时宽平台加深夜小峰、无通勤峰；电动车晚峰放大 1.2 倍。

#### 4.5.4 事故生成的泊松过程

交通事故按泊松过程生成[16]：每个刷新周期新增事故起数服从参数 λ 的泊松分布，λ 与省权重及当前时段因子成正比，即事故在高峰时段与高权重区域更密集。每起事故的类型、严重程度、涉事车辆类型由分段随机抽样确定，坐标在所属区域质心附近按区域层级不同的散布半径生成。事故具有生命周期：活跃事故列表封顶 200 条以防内存膨胀，且每周期按与严重程度负相关的结案概率移除已结案记录；"今日事故数"为当日口径、只增不减。系统启动时执行引导程序（bootstrap），依据当日已流逝小时数对双峰曲线的积分预置事故基数，并回放生成过去 24 小时的趋势序列，使大屏首屏即携带完整历史语境。

#### 4.5.5 自下而上聚合与口径保障

省与全国层级的指标不直接生成，而由下辖实体自下而上聚合：在途车辆数与今日事故数为求和聚合；平均车速以在途车辆数为权重的加权平均；拥堵指数取算术平均叠加微扰后钳制回值域。车辆类型统计满足 Σ各类型在途数 = 在途总量、Σ占比 = 100% 的闭合约束。开发构建下每个周期对全国及各省执行口径断言，一旦闭合破坏即在控制台告警。聚合只存在于引擎层，图表与 store 永不二次聚合，是 SSOT 原则在数据侧的延伸。

#### 4.5.6 引擎调度与模拟时钟

引擎以全局单例形式组织，集中配置刷新周期（默认 5000 ms）与时间加速系数（默认 60）。模拟时钟以"真实间隔 × 加速系数"推进：1 真实秒等于 60 模拟秒，24 小时趋势窗口（288 个点、5 分钟粒度）约 24 分钟真实时间滚完一轮，"当前时段"每小时推进 1 分钟——答辩演示 15 分钟即可观察完整的模拟日内规律变化，兼顾演示节奏与真实感。暂停/恢复通过清除定时器并冻结模拟时钟实现；销毁方法清理全部定时器与回调，与路由离开钩子联动防止泄漏。

缩放采用"transform 等比缩放（contain + 居中）"算法：

```text
输入：设计基准 designW=1920, designH=1080；实时视口 vw, vh

scale   = min(vw / designW, vh / designH)      # 等比取小，保证双向不溢出
offsetX = (vw − designW × scale) / 2            # 水平居中
offsetY = (vh − designH × scale) / 2            # 垂直居中

容器样式：position: fixed; left: 0; top: 0
          width: 1920px; height: 1080px（恒为设计稿像素）
          transform-origin: left top
          transform: translate(offsetX, offsetY) scale(scale)          …（4-7）
```

选择 transform 方案而弃用 rem/vw 方案的依据有三：rem 需全量换算且 ECharts 内部尺寸（字号、半径）不随 rem 自动缩放；vw 方案在非 16:9 窗口会水平溢出；transform 对 DOM 与 canvas 一视同仁，且实现收敛于单一组合函数，改动面最小。窗口尺寸变化与全屏状态切换均触发重算；留白区（letterbox）以深空背景填充，构成有意的视觉设计。经理论分析与验证，ECharts 底层 zrender 的事件定位基于 transform 后的视觉盒换算，缩放容器下点击命中与悬浮提示定位天然正确。

### 5.2 模拟数据引擎实现

数据引擎五个模块中，噪声模型与引擎调度构成算法核心。噪声通道类的核心求值方法实现如下（摘自 `src/mock/noise.ts`，有删节）：

```typescript
// src/mock/noise.ts（摘录，有删节）
export class NoiseChannel {
  value(t: number): number {
    if (t <= this.lastT) return this.lastValue          // 时钟冻结 → 输出冻结
    // 有界随机游走：累计漂移不超过 ±8% × base
    this.walk += gaussian(this.rand) * this.walkSigma
    this.walk = Math.min(this.walkMax, Math.max(-this.walkMax, this.walk))
    // 双正弦叠加波形（T₁=300s 慢波 / T₂=40s 快波，相位随机初始化）
    const wave = 1 +
      this.amp1 * Math.sin((2 * Math.PI * t) / this.period1 + this.phase1) +
      this.amp2 * Math.sin((2 * Math.PI * t) / this.period2 + this.phase2)
    let raw = this.base * wave + this.walk
    // 连续性钳制：与上一值相比变化不超过 ±15%
    raw = Math.min(this.lastValue * (1 + this.continuity),
                   Math.max(this.lastValue * (1 - this.continuity), raw))
    if (this.min !== undefined) raw = Math.max(this.min, raw)   // 业务值域钳制
    if (this.max !== undefined) raw = Math.min(this.max, raw)
    this.lastT = t
    this.lastValue = raw
    return raw
  }
}
```

该方法将式（4-1）至式（4-4）完整落地：首行的单调时间判断使"模拟时钟冻结 ⇒ 输出冻结"成为构造性质；随机游走先钳制后叠加、再经连续性与值域双重钳制的固定顺序，排除了"贴边"与数量级跳变。每个地区实体持有在途车辆、拥堵指数、平均车速三个独立噪声通道，相位互异，保证指标间波动彼此独立。时段因子及车辆类型差异化形状的实现如下：

```typescript
// src/mock/noise.ts（摘录）
const gauss = (h: number, mu: number, sigma: number) =>
  Math.exp(-((h - mu) ** 2) / (2 * sigma * sigma))

export function hourFactor(h: number): number {
  const bump = h >= 10 && h <= 16 ? Math.sin((Math.PI * (h - 10)) / 7) : 0
  return 0.16 + 0.62 * gauss(h, 8, 1.3) + 0.78 * gauss(h, 18, 1.6) + 0.3 * bump
}

export function typeHourFactor(h: number, shape: 'car'|'bus'|'truck'|'ev'): number {
  switch (shape) {
    case 'bus':   return 0.12 + 0.62 * gauss(h, 8, 1.0) + 0.75 * gauss(h, 18, 1.0)
    case 'truck': return 0.12 + (h >= 8 && h <= 17 ? 0.75 : 0.12) + 0.4 * gauss(h, 1, 1.5)
    case 'ev':    /* 晚峰放大 1.2 倍 */
    default:      return hourFactor(h)
  }
}
```

引擎调度与事故泊松生成的核心实现如下（摘自 `src/mock/engine.ts`，有删节）：

```typescript
// src/mock/engine.ts（摘录，有删节）
private tick(): void {
  this.simTime += this.config.intervalMs * this.config.accel   // 模拟时钟 60 倍加速
  this.evolveAll(this.simTime)     // 全部实体按噪声模型演化
  this.spawnAccidents()            // 泊松过程生成新增事故
  this.closeAccidents()            // 按结案概率移除已结案事故
  this.emit()                      // 自下而上聚合并推送 Snapshot
}

private spawnAccidents(): void {
  const h = hourOf(this.simTime)                                  // 小数小时
  const lambda = ENGINE_CONFIG.accidentLambdaBase * hourFactor(h)
  const n = poisson(this.world.rand, lambda)                      // 泊松抽样
  for (let i = 0; i < n; i++) {
    const target = this.pickAccidentTarget()                      // 按权重二次抽样
    target.accidentCountToday++
    this.activeAccidents.push(this.makeAccident(target, this.simTime))
  }
  if (this.activeAccidents.length > ENGINE_CONFIG.maxActiveAccidents) {
    this.activeAccidents = this.activeAccidents.slice(            // 活跃封顶 200 条
      this.activeAccidents.length - ENGINE_CONFIG.maxActiveAccidents)
  }
}
```

其中 `poisson` 采用 Knuth 乘积抽样法实现；`pickAccidentTarget` 通过预建的省—市两级累积权重表完成 O(省数) 的一次抽样，使事故落点与区域权重严格成比例。引导程序在引擎启动时先以 5 分钟步长回放过去 24 小时（每地区 288 个趋势点），再按"当日已流逝小时对双峰曲线的积分比例"预置今日事故基数并生成历史活跃事故，保证首屏数据即刻完整。聚合模块对城市执行求和/加权聚合生成省与全国实体，并在开发构建下对每轮快照执行口径断言。

**实现要点**：噪声模型以"双正弦 + 有界随机游走 + 双重钳制"从数学上保证连续性；事故生成以泊松过程 + 权重抽样保证空间与时段分布的合理性；引导回放使系统无需预热即可演示；实体演化、事故增删与聚合的职责在模块间严格分离，引擎零框架依赖、可独立单测。

### 5.3 地图三级钻取与 mapRegistry 懒加载实现

地图能力基于 ECharts 的动态注册机制构建。9 份 geoJSON（全国 + 广东/江苏/浙江/四川 4 省 + 广州/南京/杭州/成都 4 市，合计 1.49 MB）由自研脚本 `scripts/fetch-geo.mjs` 从阿里 DataV GeoAtlas（areas_v3 版本）一次性下载并裁剪 `properties` 至 name/adcode/center/centroid 四个字段后入库，经 Vite 构建为异步 chunk，运行期零在线请求。注册表的懒加载实现如下（摘自 `src/services/mapRegistry.ts`）：

```typescript
// src/services/mapRegistry.ts（摘录）
const loaders = import.meta.glob('../assets/geo/*.json')   // 路径 → 懒加载函数
const registered = new Set<number>()                       // 已注册缓存（判重）
const pending = new Map<number, Promise<boolean>>()        // 在途任务去重

export function loadGeo(code: number): Promise<boolean> {
  if (registered.has(code)) return Promise.resolve(true)   // 命中缓存，避免重复注册
  const inflight = pending.get(code)
  if (inflight) return inflight                            // 并发下钻去重
  const loader = loaders[`../assets/geo/${CODE_FILE[code]}.json`]
  if (!loader) return Promise.resolve(false)               // 未收录 → 走降级提示
  const task = loader().then(mod => {
    registerMap(String(code), mod as never)                // 以 adcode 为注册名
    registered.add(code)
    return true
  }).catch(() => false)
  pending.set(code, task)
  return task
}
```

钻取交互由 store 的 `drillDown` action 编排：先校验目标是否属于可下钻清单（4 个内置省/4 个内置市），再调用 `loadGeo` 拉取对应 chunk 并注册，成功则将 adcode 压入钻取栈触发联动，失败或未收录则置全局提示并保持视图不变。地图组件在层级切换时不销毁实例，仅以 `setOption` 原地替换 series 的 map 字段与数据，配合过渡动画避免闪烁。业务实体统一以 adcode 为主键并维护"adcode → geoJSON 名称"映射，从数据侧杜绝名称不一致导致的渲染空白。

**实现要点**：`import.meta.glob` + 异步 chunk 实现"用时才加载"的地图资源策略，首屏仅付出全国边界的体积成本；注册缓存判重与在途去重防止重复注册造成的内存泄漏；"栈 + 原地换装"的组合使三级钻取与逐级返回均无实例重建开销。

### 5.4 Pinia SSOT 与 getters 联动过滤实现

状态层以组合式语法定义唯一的 `screen` store：快照以 `shallowRef` 存放并整体替换，钻取栈与两个类型维度以 `ref` 存放，十余个视图数据 getter 以 `computed` 派生。以 KPI 联动 getter 为例（摘自 `src/stores/screen.ts`，有删节）：

```typescript
// src/stores/screen.ts（摘录，有删节）
const filteredKpi = computed(() => {
  const region = currentRegion.value        // 钻取栈顶 → 当前地区实体
  if (!region) return null
  let { activeVehicles, avgSpeed, accidentCountToday } = region
  const vt = selectedVehicleType.value      // 车辆类型维度
  if (vt) {
    activeVehicles = Math.round(
      region.vehicleTypes.find(v => v.typeCode === vt)?.activeCount ?? 0)
    avgSpeed = Math.round(avgSpeed * VEHICLE_TYPE_MAP[vt].speedFactor * 10) / 10
  }
  const at = selectedAccidentType.value     // 事故类型维度
  if (at) {
    accidentCountToday =
      scopedAccidents.value.filter(a => a.accidentType === at).length
  }
  return { congestionIndex: region.congestionIndex,
           activeVehicles, accidentCountToday, avgSpeed }
})
```

该实现严格对照表 4-2 的过滤矩阵：地区维度经 `currentRegion`（钻取栈顶）生效；车辆类型维度替换在途车辆数并按速度系数折算平均车速；事故类型维度将今日事故数切换为涉事类型明细计数；拥堵指数保持区域口径不受类型缩放。其余 getter 同理实现：路口排行在类型维度下改按类型的分型流量排序；分时热力在类型维度下按时段形状系数折算（`typeHourFactor(h)/hourFactor(h)`）；地图散点同时受两个类型维度过滤。引擎接线方面，视图挂载时创建引擎并注入 `applyTick` 回调，快照经浅层引用替换写入；路由离开时执行引擎销毁与快照清空。

**实现要点**：全部联动逻辑收敛为"过滤状态 ref → computed getters"的纯函数式派生，无事件总线、无组件间直接通信；`shallowRef` 整体替换避免了对深层数据的代理开销；任一维度变化后相关 getter 精确重算、无关 getter 缓存命中，联动刷新成本与变化范围成正比。

### 5.5 useECharts 图表实例生命周期托管实现

12 个图表组件共享同一实例托管组合函数，其核心实现如下（摘自 `src/composables/useECharts.ts`，有删节）：

```typescript
// src/composables/useECharts.ts（摘录，有删节）
onMounted(() => {
  const el = domRef.value
  if (!el) return
  instance.value = init(el, 'neon')            // 初始化并应用霓虹主题
  instance.value.setOption(options.optionFactory())   // 挂载即首刷
  if (options.onChartClick) instance.value.on('click', options.onChartClick)
  observer = new ResizeObserver(() => {        // 容器尺寸变化 → 防抖 resize
    if (resizeTimer) clearTimeout(resizeTimer)
    resizeTimer = setTimeout(() => instance.value?.resize(), 150)
  })
  observer.observe(el)
})
if (options.watchDeps.length > 0) {
  watch(options.watchDeps, refresh)            // 数据驱动 setOption（merge 模式）
}
onBeforeUnmount(() => {                        // 卸载四件事原子完成
  if (resizeTimer) clearTimeout(resizeTimer)
  observer?.disconnect()
  instance.value?.dispose()
  instance.value = null
})
```

托管函数将"初始化 + 首刷、响应式数据驱动更新、防抖自适应、卸载清理"收敛为唯一入口：图表组件仅需提供容器引用、option 工厂函数与响应式依赖数组。数据更新默认采用 merge 模式的 `setOption`，仅合并变化的 series.data 而非整屏重设，配合 Vue 在同一微任务内的批处理调度，单周期十余个图表的重绘天然合帧。

**实现要点**：实例、观察器与定时器的生命周期严格同生共死，卸载路径原子完成清理，是两小时长时运行无泄漏的结构性保障；ResizeObserver 防抖 150 ms 避免连锁 resize 风暴；组件代码零 ECharts 生命周期样板，图表新增成本降至"一个 option 工厂"。

### 5.6 useScreenAdapter 等比缩放实现

屏幕适配组合函数按式（4-7）实现（摘自 `src/composables/useScreenAdapter.ts`）：

```typescript
// src/composables/useScreenAdapter.ts（摘录）
export function useScreenAdapter(designW = 1920, designH = 1080) {
  const state = reactive({ scale: 1, offsetX: 0, offsetY: 0 })
  const compute = (): void => {
    const vw = window.innerWidth
    const vh = window.innerHeight
    const scale = Math.min(vw / designW, vh / designH)   // 等比取小（contain）
    state.scale = scale
    state.offsetX = (vw - designW * scale) / 2           // 双向居中偏移
    state.offsetY = (vh - designH * scale) / 2
  }
  const onResize = () => { if (timer) clearTimeout(timer)
                           timer = setTimeout(compute, 100) }   // 防抖 100 ms
  onMounted(() => {
    compute()
    window.addEventListener('resize', onResize)
    window.addEventListener('fullscreenchange', compute)  // 全屏切换即时重算
  })
  /* onBeforeUnmount：移除两监听并清理定时器（略） */
  const containerStyle = computed(() => ({
    position: 'fixed', left: '0', top: '0',
    width: `${designW}px`, height: `${designH}px`,
    transform: `translate(${state.offsetX}px, ${state.offsetY}px) scale(${state.scale})`,
    transformOrigin: 'left top'
  }))
  return { containerStyle, adapter: state }
}
```

内层容器尺寸恒为设计稿像素（1920×1080），全部子元素的 px 布局因此绝对稳定；缩放系数与居中偏移经响应式状态驱动 `transform` 实时生效。`min` 取小保证任一方向不溢出裁切：1366×768 下缩放系数约 0.711，最小字号仍可辨认；2560×1440 下系数 1.333，矢量 DOM 与高分屏 canvas 渲染放大无失真。

**实现要点**：缩放逻辑全部收敛于单一组合函数，布局层像素写死、内外分工明确；resize 防抖与 fullscreenchange 双触发覆盖窗口拖拽与全屏两类场景；经早期验证确认 transform 容器下 ECharts 事件与悬浮提示定位正确，方案风险前置消除。

## 第七章 总结与展望

### 7.1 工作总结

本文完成了纯前端城市交通监控可视化大屏的需求分析、系统设计、编码实现与测试验证，形成了一套断网可完整运行的大屏工程方案。系统以 Vue 3.5 组合式 API 与 TypeScript 5.8 严格模式为工程基座，以 Vite 6 构建、Pinia 2 单一数据源状态管理、Vue Router 4 hash 路由与 ECharts 5.6 按需渲染为技术支撑，交付了 12 个视图组件、2 个组合式函数、1 个 Pinia store 与 5 模块模拟数据引擎的完整实现。

在地图钻取方面，系统基于"geoJSON 本地打包 + import.meta.glob 懒加载 + registerMap 动态注册 + 实例原地换装"的组合方案实现了全国—省—市三级钻取与逐级返回，9 份边界数据合计 1.49 MB 且仅全国边界参与首屏，未收录区域以明确提示友好降级，兼顾了交互深度、首屏性能与离线约束。在多图表联动方面，系统以 SSOT 原则将钻取栈与双类型过滤收敛于唯一 store，十余个 getter 按三维度过滤矩阵纯函数式派生视图数据，任一入口的选择同步作用于全屏，聚合口径闭合误差小于 0.2%，从机制上杜绝了口径漂移。在实时刷新方面，系统以"双正弦 + 有界随机游走 + 双重钳制"的平滑噪声模型与双峰高斯时段因子驱动 5 秒周期数据演化，模拟时钟 60 倍加速使 24 分钟即可观察完整日内规律，实测相邻快照最大变化 2.37%、峰谷比 5.9，暂停恢复无缝衔接。

工程验证方面，系统通过了 6 项 node:test 数据质量自动化测试与 15 项代表性功能走查，首屏 gzip 约 470 KB 且 3 秒内完成渲染，两小时长时运行帧率与内存稳定。上述结果表明，纯前端技术路线在演示型大屏场景下能够达到接近生产系统的交互质量与数据可信度。

### 7.2 不足与展望

受限于毕业设计周期与纯前端定位，系统仍存在以下不足，同时也是后续演进的方向。

其一，数据来源方面。当前系统完全依赖内置模拟引擎，数据的"真实感"建立在数学模型之上而非真实观测。后续可接入 WebSocket/SSE 实时通道对接卡口与浮动车数据，将模拟引擎降级为断网兜底模式，平滑过渡到真实数据驱动；届时平滑噪声模型亦可复用为数据清洗与异常平滑组件。

其二，地图覆盖方面。geoJSON 仅内置全国与 4 省 4 市，其余区域下钻时只能降级提示。后续可将 34 个省级与重点城市边界全量入库，并引入边界化简与矢量瓦片技术控制总体积，实现全国任意省市的无差别钻取。

其三，可视化形态方面。现有图表以二维平面为主，对高架、立交、隧道等立体交通结构的表达能力有限。后续可引入 WebGL（如 ECharts GL 的三维地理组件）呈现城市三维路网与体量化的流量渲染，并探索数字孪生形态的指挥大屏。

其四，智能化方面。大屏目前是纯展示与过滤型界面，尚不具备分析问答能力。后续可集成大语言模型问答入口，支持以自然语言完成"下钻到拥堵最严重的城市""对比两省事故构成"等意图的自动编排，使大屏从"被人看的屏"演进为"可对话的助手"。

总体而言，本系统以扎实的工程实践验证了纯前端路线在交通态势可视化领域的可行性，其架构模式（SSOT 联动、懒加载地图、模拟数据引擎）对同类大屏开发具有直接的参考与复用价值。
