# 基于微服务架构的个人任务完成情况跟踪系统设计与实现

---

## 摘要

随着移动互联网与远程办公的普及，个人任务管理工具已成为大学生与职场人群日常效率提升的重要辅助。然而，现有主流任务管理应用多采用单体架构，存在扩展性差、模块耦合度高、二次开发困难等问题，且普遍缺乏对任务完成情况的多维度统计与趋势分析能力。针对上述问题，本文设计并实现了一个基于微服务架构的个人任务完成情况跟踪系统。

系统采用 Node.js + TypeScript 技术栈，将业务拆分为用户服务（user-service）、任务服务（task-service）、跟踪服务（tracking-service）和报表服务（report-service）四个独立微服务。各服务拥有独立数据库，通过 RESTful API 通信，使用 JWT 实现无状态鉴权，采用 SQLite 作为嵌入式数据库以降低部署门槛。系统实现了用户注册登录、任务全生命周期管理、任务状态流转审计、完成事件追溯以及日/周/月多维度统计报表等核心功能。在跨服务数据一致性方面，系统采用 Outbox 模式结合后台重试机制实现最终一致性；在分页查询方面，采用游标分页替代传统偏移量分页，避免数据变动时的页码错位问题。

测试结果表明，系统各微服务可独立启动与部署，核心接口响应时间满足设计要求，单元测试覆盖率达到预期目标。本文的研究工作验证了微服务架构在中小型个人效率工具场景下的可行性，为同类系统的设计与实现提供了参考。

**关键词**：微服务；Node.js；任务管理；JWT；游标分页；最终一致性

---

## Abstract

With the popularization of mobile Internet and remote work, personal task management tools have become essential assistants for college students and professionals to improve daily productivity. However, most existing task management applications adopt a monolithic architecture, which suffers from poor scalability, high module coupling, and difficulty in secondary development. Moreover, they generally lack multi-dimensional statistics and trend analysis of task completion. To address these issues, this paper designs and implements a personal task completion tracking system based on a microservices architecture.

The system uses Node.js and TypeScript, splitting the business into four independent microservices: user-service, task-service, tracking-service, and report-service. Each service has its own database and communicates via RESTful APIs. Stateless authentication is implemented using JWT, and SQLite is used as an embedded database to lower deployment barriers. The system implements core features including user registration and login, task lifecycle management, task status transition auditing, completion event tracing, and daily/weekly/monthly statistical reports. For cross-service data consistency, the system adopts the Outbox pattern combined with a background retry mechanism to achieve eventual consistency. For pagination, cursor-based pagination is used instead of traditional offset pagination to avoid page misalignment caused by data changes.

Testing results show that each microservice can be independently started and deployed, core API response times meet design requirements, and unit test coverage reaches the expected target. This work verifies the feasibility of microservices architecture in small-to-medium personal productivity tool scenarios and provides a reference for the design and implementation of similar systems.

**Keywords**: Microservices; Node.js; Task Management; JWT; Cursor Pagination; Eventual Consistency

## 第1章 绪论

### 1.1 研究背景与意义

在快节奏的现代生活中，个人每天需要处理学习、工作、生活等多方面的事务。根据相关调研，具备明确任务管理习惯的人群在目标达成率上显著高于无计划人群。然而，传统的待办事项应用往往仅提供简单的"待办-完成"二元状态管理，缺乏对任务完成过程的量化追踪与数据分析，用户无法直观地了解自己在一段时间内的任务完成效率、分类分布以及趋势变化。

与此同时，软件架构正在经历从单体架构向微服务架构的演进。单体架构虽然开发简单，但随着业务复杂度增长，代码库膨胀、模块耦合、部署耦合等问题日益突出。微服务架构将系统拆分为多个小型、独立部署的服务，每个服务围绕特定业务能力构建，拥有独立的数据存储，通过轻量级机制通信。这种架构天然支持独立扩展、独立部署和技术栈异构，已成为大型互联网应用的主流架构选择。

本课题以"个人任务完成情况跟踪"为业务场景，采用微服务架构进行系统设计与实现，具有以下意义：

第一，**实践价值**。系统面向大学生与职场人群的真实需求，提供任务管理与完成情况统计的完整功能，具备实际使用价值。

第二，**教学价值**。系统涵盖了微服务架构的核心要素——服务拆分、独立数据库、REST 通信、JWT 鉴权、跨服务数据一致性、容器化部署等，是一个完整的微服务教学案例。

第三，**技术探索价值**。在个人效率工具这一轻量级场景下采用微服务架构，探讨微服务架构在中小型应用中的适用性与权衡，具有一定的实践参考意义。

### 1.2 国内外研究现状

在任务管理工具领域，国外主流产品如 Todoist、Things、Microsoft To Do 等已经发展成熟，提供了任务分类、优先级、截止日期、提醒等丰富功能。在完成情况统计方面，部分产品提供了简单的完成率报表，但普遍缺乏多维度趋势分析。在架构层面，这些产品多采用后端服务+前端应用的分层架构，部分引入了微服务拆分，但核心统计功能通常与任务管理模块紧耦合。

在微服务架构研究方面，Martin Fowler 于 2014 年正式提出微服务架构概念，随后Netflix、Amazon、Netflix 等公司在生产环境中大规模实践了微服务架构。国内阿里、美团、京东等互联网企业也广泛采用微服务架构，并在服务注册发现、配置中心、链路追踪等方面积累了丰富经验。在跨服务数据一致性方面，业界提出了 Saga 模式、Outbox 模式、事件溯源等多种解决方案，其中 Outbox 模式因其实现简单、与本地事务天然结合的特点，在中小型微服务系统中被广泛采用。

在分页查询方面，传统的 LIMIT/OFFSET 分页在数据量增大和并发写入场景下存在性能问题和数据错位问题，游标分页（Cursor-based Pagination）通过记录上一页最后一条记录的位置作为游标，避免了上述问题，已成为 GitHub API、Twitter API 等大型开放 API 的标准分页方案。

## 第2章 相关技术介绍

### 2.1 Node.js 运行时

Node.js 是一个基于 Chrome V8 引擎的 JavaScript 运行时环境，采用事件驱动、非阻塞 I/O 模型，使其在 I/O 密集型场景下具有高性能优势。自 Node.js 18 版本起，原生内置了 fetch API，无需引入额外的 HTTP 客户端库即可发起 HTTP 请求，这对于微服务间的通信非常便利。Node.js 的包管理生态 npm 是世界上最大的开源库生态系统，提供了丰富的中间件与工具库。

本系统选择 Node.js 18 LTS 版本作为运行时，主要基于以下考虑：（1）前后端统一使用 JavaScript/TypeScript 语言，降低开发与维护成本；（2）原生 fetch 简化了服务间 HTTP 调用；（3）npm workspaces 原生支持 Monorepo 管理，适合多微服务项目。

### 2.2 TypeScript 语言

TypeScript 是 JavaScript 的超集，通过静态类型系统在编译期捕获类型错误，提升代码的可维护性与重构安全性。TypeScript 5.x 支持严格模式（strict mode），开启后会强制检查 null/undefined、隐式 any 等常见问题。在微服务架构中，各服务间通过 API 契约通信，TypeScript 的类型系统可以在编译期保证请求与响应的数据结构正确性，减少运行时错误。

本系统在 tsconfig.base.json 中开启 strict 模式，禁止使用 any 类型，所有 API 请求与响应均有明确的 TypeScript 类型定义。

### 2.3 Express 框架

Express 是 Node.js 生态中最流行的 Web 框架，以其简洁的路由定义、灵活的中间件模型和庞大的中间件生态著称。Express 的中间件模型采用洋葱模型，请求依次经过各中间件处理，非常适合实现鉴权、日志、错误处理等横切关注点。

本系统使用 Express 4 作为 Web 框架，通过中间件链实现请求 ID 注入、JWT 鉴权、zod 参数校验、统一错误处理等横切逻辑。

### 2.4 SQLite 数据库

SQLite 是一个嵌入式关系型数据库，整个数据库存储在单个文件中，无需独立的数据库服务进程。better-sqlite3 是 Node.js 中对 SQLite 的同步绑定，其同步 API 简化了事务处理——在 better-sqlite3 中，事务是同步执行的，无需 await，这使得跨表事务代码更加直观。

本系统为每个微服务分配独立的 SQLite 数据库文件，既满足了微服务"独立数据库"的架构原则，又避免了运维独立数据库服务的开销，适合毕设项目的规模。

### 2.5 JWT 鉴权

JSON Web Token（JWT）是一种开放的、基于 JSON 的开放标准（RFC 7519），用于在各方之间安全地传输信息。JWT 由 Header、Payload、Signature 三部分组成，服务端使用密钥对 Payload 进行签名，客户端在后续请求中携带 Token，服务端验证签名即可确认身份，无需查询会话存储。

在微服务架构中，JWT 的无状态特性尤为重要——各微服务使用共享的 JWT_SECRET 即可本地验证 Token，无需每次都调用用户服务进行鉴权，大大降低了服务间的耦合与延迟。

### 2.6 微服务架构

微服务架构是一种将单一应用程序开发为一组小型服务的方法，每个服务运行在独立的进程中，服务间通过轻量级机制（通常是 HTTP RESTful API）通信。各服务围绕特定业务能力构建，独立部署、独立扩展，拥有独立的数据存储。

微服务架构的核心原则包括：单一职责、服务独立部署、去中心化数据管理、故障隔离、轻量级通信。其主要优势在于：技术栈异构、独立扩展、故障隔离、团队自治。主要挑战在于：分布式复杂性（网络延迟、部分失败、数据一致性）、运维复杂性（多服务部署、监控、链路追踪）。

本系统在个人任务管理这一中小型场景下实践微服务架构，通过 Outbox 模式解决跨服务数据一致性问题，通过配置式服务发现（环境变量注入）避免引入服务注册中心的复杂性。

### 2.7 Docker 容器化

Docker 是一个开源的应用容器引擎，将应用及其依赖打包到一个轻量级、可移植的容器中。docker-compose 是 Docker 官方提供的多容器编排工具，通过 YAML 文件定义多个服务及其网络、卷、依赖关系，一键启动整个系统。

本系统为每个微服务编写独立的 Dockerfile（多阶段构建，builder 阶段编译 TypeScript，runner 阶段仅保留生产依赖与编译产物），通过 docker-compose 编排 4 个服务及共享网络与数据卷。

## 第3章 需求分析

### 3.1 系统定位

本系统定位为面向个人用户的任务完成情况跟踪工具，核心价值在于不仅管理"要做什么"，更追踪"完成得怎么样"。系统不涉及团队协作、消息推送、第三方日历同步等功能，专注于个人场景的任务管理与完成情况量化分析。

### 3.2 功能需求

#### 3.2.1 用户管理

（1）用户注册：用户提供用户名、邮箱、密码进行注册。用户名长度 3-30 位，仅含字母数字下划线；密码长度≥8 且必须同时包含字母与数字；用户名与邮箱全局唯一。

（2）用户登录：用户使用用户名或邮箱配合密码登录，登录成功后系统签发 JWT Token，有效期 7 天。登录失败时不区分"用户不存在"与"密码错误"，统一返回"用户名或密码错误"，防止用户枚举攻击。

（3）个人信息管理：登录用户可查看与更新个人信息（邮箱、昵称），但禁止通过此接口修改密码。

#### 3.2.2 任务管理

（1）创建任务：用户创建任务时需提供标题（必填，≤100 字）、描述（可选，≤2000 字）、分类（可选）、优先级（低/中/高/紧急，默认中）、截止日期（可选，须晚于当前时间）。任务创建后初始状态为待办（TODO）。

（2）任务编辑与删除：用户可编辑或删除自己的任务，不可操作他人任务。

（3）任务列表查询：用户可分页查询自己的任务列表，支持按分类、优先级、状态过滤，采用游标分页。

（4）任务状态流转：任务状态按 TODO → IN_PROGRESS → DONE 单向流转，允许从 DONE 重新打开为 IN_PROGRESS（重新完成），但禁止回退到 TODO。状态流转时系统自动记录状态变更日志；流转为 DONE 时记录完成事件。

#### 3.2.3 完成跟踪

（1）完成事件记录：任务被标记为 DONE 时，自动记录一条完成事件（含任务 ID、用户 ID、完成时间）。

（2）完成历史查询：用户可分页查询自己的完成事件列表，支持按任务过滤。

（3）完成进度查询：用户可查看当前的任务完成进度，包括待办数、进行中数、已完成数以及完成率。

（4）状态变更日志：任务每次状态流转都记录审计日志，用户可查询某任务的状态变更历史。

#### 3.2.4 统计报表

（1）完成汇总：指定时间段内的完成总数、任务总数、完成率。

（2）周期报表：按日/周/月聚合完成数量。

（3）趋势分析：按指定周期（日/周/月）展示完成率变化趋势。

（4）时间范围校验：统计查询的开始日期不得晚于结束日期，时间跨度不得超过 366 天。

### 3.3 非功能需求

#### 3.3.1 性能需求

所有核心 API 在正常负载下响应时间 P95 < 200ms；单实例支持≥100 QPS。

#### 3.3.2 安全需求

（1）密码必须以 bcrypt 不可逆加密存储，禁止明文落库。
（2）除注册、登录、健康检查接口外，所有接口必须校验 JWT Token。
（3）所有接口入参必须经过类型与格式校验。
（4）用户只能访问属于自己的数据，禁止跨用户访问。

#### 3.3.3 可靠性需求

（1）服务间调用超时时间 3 秒，网络错误重试 1 次。
（2）task-service 调用 tracking-service 失败时，任务状态更新不受影响，通过 Outbox 机制补偿，实现最终一致性。
（3）单服务故障不影响其他服务的核心功能。

#### 3.3.4 可部署性需求

（1）每个微服务提供独立 Dockerfile。
（2）提供 docker-compose.yml 一键启动全部 4 个服务。
（3）各服务可独立构建、独立部署、独立启停。

### 3.4 用例分析

系统的主要参与者为终端用户，其核心用例包括：注册账号、登录系统、创建任务、编辑任务、删除任务、查看任务列表、更新任务状态、查看完成进度、查看完成历史、查看统计报表。

其中，"更新任务状态"是核心用例，涉及 task-service 与 tracking-service 的跨服务协作：task-service 更新任务状态后，需通知 tracking-service 记录完成事件与状态日志。该用例的成功执行不依赖于 tracking-service 的实时可用性——即使 tracking-service 暂时不可用，task-service 仍会成功更新任务状态，待 tracking-service 恢复后通过 Outbox 重试机制补录事件。

## 第4章 系统设计

### 4.1 总体架构设计

系统采用微服务架构，由 4 个业务微服务与 1 个共享包组成。终端用户通过 HTTP/REST 直接访问各服务，不设置独立 API 网关，鉴权由各服务中间件统一执行。服务间通过 REST API 同步调用，服务发现采用配置式（环境变量注入服务地址）。

系统架构如图 4-1 所示。user-service 负责用户注册、登录与 JWT 签发；task-service 负责任务 CRUD 与状态流转；tracking-service 负责完成事件记录、状态日志与进度查询；report-service 负责多维度统计报表，其数据来源于 tracking-service 与 task-service 的实时聚合。

服务间调用关系如下：
- task-service → tracking-service：任务状态变更时记录完成事件与状态日志。
- tracking-service → task-service：进度查询时获取各状态任务计数。
- report-service → tracking-service：报表查询时获取完成事件数据。
- report-service → task-service：报表查询时获取任务总数与分类计数。

### 4.2 微服务拆分

系统按业务领域拆分为 4 个微服务，各服务职责边界清晰：

**user-service（用户服务，端口 3001）**：负责用户注册、登录、JWT 签发、个人信息管理。拥有 users 表。核心接口包括 POST /register、POST /login、GET/PUT /profile。

**task-service（任务服务，端口 3002）**：负责任务的创建、编辑、删除、查询与状态流转。拥有 tasks 表与 outbox 表（跨服务调用补偿）。核心接口包括任务 CRUD、PATCH /tasks/:id/status。

**tracking-service（跟踪服务，端口 3003）**：负责完成事件记录、状态变更日志记录与查询、完成进度查询。拥有 completions 表与 status_logs 表。核心接口包括 POST /completions（内部）、GET /progress、GET /completions。

**report-service（报表服务，端口 3004）**：负责多维度统计报表。无独立持久化存储，所有数据通过实时聚合 tracking-service 与 task-service 的接口数据计算得出。核心接口包括 GET /summary、GET /daily、GET /weekly、GET /monthly、GET /trend。

### 4.3 数据库设计

#### 4.3.1 users 表（user-service）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| user_id | TEXT | PRIMARY KEY | 用户唯一标识（UUID） |
| username | TEXT | NOT NULL UNIQUE | 用户名 |
| email | TEXT | NOT NULL UNIQUE | 邮箱 |
| password_hash | TEXT | NOT NULL | bcrypt 加密后的密码哈希 |
| nickname | TEXT | | 昵称 |
| created_at | TEXT | NOT NULL | 创建时间（ISO8601） |
| updated_at | TEXT | NOT NULL | 更新时间 |

#### 4.3.2 tasks 表与 outbox 表（task-service）

tasks 表字段包括 task_id（主键）、user_id（归属用户）、title（标题）、description（描述）、category（分类）、priority（优先级，默认 medium）、status（状态，默认 TODO）、due_date（截止日期）、created_at、updated_at。索引建立在 (user_id, created_at)、(user_id, status)、(user_id, category) 上，以支持用户维度的列表查询与过滤。

outbox 表用于跨服务调用的最终一致性补偿，字段包括 id（自增主键）、event_type（事件类型：COMPLETION/STATUS_LOG/DELETE）、payload（JSON 格式的事件载荷）、target_url（目标地址）、status（PENDING/SENT/FAILED）、retries（已重试次数）、created_at、next_retry_at（下次重试时间）。

#### 4.3.3 completions 表与 status_logs 表（tracking-service）

completions 表记录任务完成事件，字段包括 event_id（主键）、task_id、user_id、completed_at。status_logs 表记录任务状态变更审计日志，字段包括 log_id（主键）、task_id、user_id、from_status、to_status、changed_at。两表均在 (user_id, task_id, time) 与 (user_id, time) 上建立复合索引，支持按用户、按任务、按时间的多维查询。

### 4.4 统一响应与错误码设计

所有接口响应统一封装为 `{ code, message, data }` 结构：code=0 表示成功，非零表示业务错误码，此时 data=null。系统定义了 12 个通用错误码，避免错误码爆炸：

| 错误码 | 含义 | HTTP 状态码 |
|--------|------|------------|
| 0 | 成功 | 200 |
| 1001 | 参数错误 | 400 |
| 1002 | 未认证 | 401 |
| 1003 | 无权限 | 403 |
| 1004 | 内部调用未授权 | 401 |
| 2002 | 用户名或密码错误 | 401 |
| 2003 | 用户名或邮箱已存在 | 409 |
| 2004 | 邮箱已占用 | 409 |
| 3001 | 任务不存在或无权限 | 404 |
| 4001 | 非法状态流转 | 400 |
| 5001 | 服务器内部错误 | 500 |
| 5031 | 下游服务不可用 | 503 |

### 4.5 安全设计

#### 4.5.1 JWT 鉴权流程

用户登录成功后，user-service 使用 JWT_SECRET 对 payload（{ userId, username }）进行签名，生成有效期 7 天的 JWT Token 返回给客户端。客户端在后续请求中通过 Authorization: Bearer <token> 头携带 Token。各微服务的 authenticate 中间件使用相同的 JWT_SECRET 本地验证 Token 签名与有效期，验证通过后将 payload 注入 req.user，无需调用 user-service。

#### 4.5.2 密码加密

用户注册时，密码通过 bcrypt（cost factor=10）进行不可逆哈希后存储。登录时通过 bcrypt.compare 比对明文密码与存储的哈希值，全程不接触明文密码存储。密码复杂度由 zod schema 在注册接口强制校验。

#### 4.5.3 服务间调用信任

微服务间的内部调用（如 task-service 通知 tracking-service 记录事件）通过 X-Internal-Token 请求头传递信任令牌。各服务持有相同的 INTERNAL_TOKEN 环境变量，内部写入接口校验该 Token，校验通过则跳过 JWT 校验。该令牌不对外暴露，防止外部用户伪造内部调用。

#### 4.5.4 越权防护

所有资源访问在 service 层校验 resource.userId === req.user.userId。查询接口在 SQL 层面强制 WHERE user_id = ?，从根本上隔离数据。对于不存在或无权限的资源，统一返回 3001（任务不存在），不区分"不存在"与"无权限"，防止资源枚举攻击。

### 4.6 容错与最终一致性设计

#### 4.6.1 Outbox 模式

task-service 在任务状态流转时需要通知 tracking-service 记录事件。为保证主流程不被下游故障阻塞，系统采用 Outbox 模式：

（1）task-service 在本地 SQLite 事务中同时完成任务状态更新与 outbox 记录写入，保证两者原子性。
（2）事务提交后，同步调用 tracking-service。
（3）调用成功：删除 outbox 记录。
（4）调用失败：outbox 记录保留为 PENDING 状态，由后台 worker 每 30 秒扫描并重试，最多重试 5 次，采用指数退避（30s/60s/120s/300s/600s），超过后标记为 FAILED 待人工处理。
（5）主流程无论 tracking-service 是否成功，均向用户返回成功（最终一致性）。

#### 4.6.2 超时与重试

所有服务间 HTTP 调用通过 shared 包的 HttpClient 类封装，默认超时 3000ms，通过 AbortController 实现超时控制。对网络错误（连接超时、连接拒绝）自动重试 1 次，间隔 500ms；对业务错误码（4xx/5xx）不重试，直接抛出 AppError。

#### 4.6.3 游标分页

系统所有列表接口采用游标分页替代传统偏移量分页。游标通过 base64 编码 JSON 对象（{ sortField, sortValue }）生成，sortValue 为上一页最后一条记录的排序字段值（如 created_at）。查询时使用 WHERE created_at < ? 条件，避免了 OFFSET 分页在数据变动时的错位问题，同时在大偏移量场景下具有更好的查询性能。

## 第5章 系统实现

### 5.1 共享包实现

shared 包（@task-tracker/shared）作为 npm workspace 本地包被 4 个微服务共同依赖，封装了跨服务共享的类型定义、响应包装器、游标分页工具、错误码与异常类、HTTP 客户端与结构化日志。

（1）**types.ts**：定义 ApiResponse<T>、PaginatedResponse<T>、PageQuery 接口，以及 Priority、TaskStatus、Period 枚举与 JwtPayload 接口。

（2）**errorCodes.ts**：定义错误码常量对象与 AppError 异常类（含 code、message、httpStatus 字段），以及 toHttpStatusCode 函数实现错误码到 HTTP 状态码的映射。

（3）**response.ts**：提供 ok(data, message) 与 fail(code, message) 两个工具函数，统一构造成功与失败响应。

（4）**pagination.ts**：实现 encodeCursor/decodeCursor 游标编解码与 buildPaginatedResponse 分页结果构建。游标使用 base64url 编码，解码失败时抛出 1001 参数错误。

（5）**httpClient.ts**：基于原生 fetch + AbortController 实现超时控制，自动注入 X-Internal-Token 头，网络错误自动重试，业务错误码不重试。

（6）**logger.ts**：基于 pino 创建结构化日志实例，requestIdMiddleware 为每个请求生成唯一 requestId 并注入日志上下文。

### 5.2 user-service 实现

user-service 采用经典的三层架构：路由层（Routes）→ 控制器层（Controller）→ 服务层（Service）→ 数据访问层（Model）。

**注册流程**：用户提交用户名、邮箱、密码后，路由层通过 zod schema 校验输入格式（用户名 3-30 位字母数字下划线、邮箱格式、密码≥8 含字母与数字）。Service 层检查用户名与邮箱唯一性，通过 bcrypt.hash(password, 10) 加密密码，生成 UUID 作为 user_id，写入 users 表。

**登录流程**：Service 层通过 findByAccount 方法同时按用户名或邮箱查询用户。若用户不存在或密码比对失败，统一抛出 2002 错误（不区分具体原因）。验证通过后，使用 jsonwebtoken.sign 签发有效期 7 天的 JWT Token。

**鉴权中间件**：authenticate 中间件从 Authorization 头提取 Bearer Token，调用 jwt.verify 验证签名与有效期。验证成功后将 payload 注入 req.user；失败时抛出 1002 错误。

### 5.3 task-service 实现

task-service 是系统中最复杂的服务，核心在于任务状态机与 Outbox 补偿机制。

**状态机实现**：statusMachine.ts 定义了合法状态流转表——TODO 可流转到 IN_PROGRESS 或 DONE，IN_PROGRESS 可流转到 DONE，DONE 可重新打开为 IN_PROGRESS。isValidTransition 函数判断流转合法性，非法流转抛出 4001 错误。

**状态流转核心逻辑**：updateStatus 方法首先校验任务归属（防止越权操作他人任务），然后校验状态流转合法性。在本地 SQLite 事务中更新任务状态与更新时间。事务提交后，若新状态为 DONE，同步调用 tracking-service 的 recordCompletion 接口记录完成事件；无论是否为 DONE，都调用 recordStatusLog 记录状态变更日志。若调用失败，将事件写入 outbox 表由后台重试。

**Outbox 重试 Worker**：startOutboxRetryWorker 函数启动一个 setInterval 定时器，每 30 秒扫描 outbox 表中状态为 PENDING 或 FAILED 且 next_retry_at 已到期的记录，逐条重试调用目标 URL。重试成功后标记为 SENT；重试失败则根据已重试次数计算下次重试时间（指数退避），超过 5 次后标记为 FAILED。

**任务列表查询**：listByUser 方法支持按分类、优先级、状态过滤，采用游标分页——解码 cursor 获取 sortValue，在 SQL 中添加 WHERE created_at < ? 条件，按 created_at 倒序取出 limit+1 条记录，由 buildPaginatedResponse 判断是否有下一页。

### 5.4 tracking-service 实现

tracking-service 负责记录与查询完成事件和状态日志。

**内部写入接口**：POST /completions 与 POST /status-logs 接口挂载 authenticateInternal 中间件，校验 X-Internal-Token。这些接口仅供 task-service 内部调用，不对外暴露。

**用户查询接口**：GET /completions、GET /progress、GET /status-logs 接口挂载 authenticate 中间件校验 JWT。查询时强制按 req.user.userId 过滤，从 SQL 层面保证数据隔离。

**进度查询**：getProgress 方法通过 TaskClient 调用 task-service 的内部聚合接口 GET /tasks/internal/count-by-status 获取各状态任务计数，然后计算完成率 = done / (todo + inProgress + done)，分母为 0 时返回 0。

### 5.5 report-service 实现

report-service 无独立数据库，所有数据通过实时聚合下游服务接口计算得出。

**汇总统计**：summary 方法并行调用 tracking-service 获取时间范围内的完成事件列表与 task-service 获取任务状态计数，计算 totalCompleted（完成事件数）、totalTasks（任务总数）与 completionRate。

**周期报表**：aggregator.ts 提供纯函数 aggregateDaily、aggregateWeekly、aggregateMonthly，将完成事件列表按日/周/月分桶聚合。按周聚合时使用 ISO 周计算逻辑。这些纯函数易于单元测试。

**趋势分析**：trend 方法按指定周期（daily/weekly/monthly）分桶，计算每个时间桶的完成率。

**时间范围校验**：zod schema 校验 startDate ≤ endDate 且时间跨度不超过 366 天，防止全表扫描。

### 5.6 容器化实现

每个微服务的 Dockerfile 采用多阶段构建：builder 阶段基于 node:18-alpine 安装依赖并编译 TypeScript；runner 阶段仅复制 dist 目录与生产依赖，镜像体积控制在较小范围。docker-compose.yml 定义 4 个服务，通过共享 bridge 网络互联，服务间通过服务名解析（如 http://tracking-service:3003/api）。各服务挂载独立的数据卷持久化 SQLite 文件，配置 healthcheck 健康检查与 depends_on 启动依赖。

### 6.3 非功能测试

#### 6.3.1 安全性测试

（1）密码存储验证：直接查询数据库 users 表，确认 password_hash 字段为 bcrypt 哈希值（以 $2b$ 开头），不存在明文密码。

（2）JWT 鉴权验证：不携带 Token 或携带伪造 Token 访问受保护接口，均返回 1002 错误。

（3）越权访问验证：用户 A 携带自己的 Token 查询用户 B 的任务，返回 3001 错误，不泄露用户 B 的数据。

（4）内部接口保护验证：不携带 X-Internal-Token 调用 /api/tracking/completions，返回 1004 错误。

#### 6.3.2 容错测试

（1）tracking-service 不可用时标记任务完成：停止 tracking-service 后，调用 task-service 的 PATCH /tasks/:id/status 接口流转到 DONE，接口仍返回成功。恢复 tracking-service 后，outbox 重试 Worker 自动补录完成事件与状态日志。

（2）report-service 在 tracking-service 不可用时返回 5031 错误，提示"下游服务不可用"。

### 6.4 测试结论

经过上述功能测试与非功能测试，系统在以下方面满足设计要求：

（1）用户注册、登录、鉴权功能正确，密码加密存储，越权访问被正确拦截。
（2）任务 CRUD 与状态机流转正确，非法流转被拒绝，Outbox 补偿机制在下游服务恢复后正确补录数据。
（3）完成进度查询与统计报表功能正确，数据来源于下游服务实时聚合。
（4）统一响应格式与错误码规范在所有接口中一致。
（5）各微服务可独立启动，服务间通过配置的地址正确通信。
