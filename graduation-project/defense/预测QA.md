## A. 技术选型类（6 题）

**A1. 为什么用 Vue 而不用 React？**

- Vue 3 组合式 API 的 `setup` + `ref/computed/watch` 让"数据流"显式可读，与本项目"引擎 tick → Store → watch → setOption"的单向管道天然契合；
- Vue 的响应式调度会把同一 tick 内的全部 watcher 合并到一次 flush 批处理执行，12 个组件联动重绘"天然合帧"，这点对本项目的 NFR-04（单次刷新阻塞 < 100ms）是结构性红利；
- 生态匹配：ECharts 官方与社区对 Vue3 的封装实践成熟，Pinia/vue-router 同属官方全家桶，TS 类型开箱即用；
- 诚实补充：React 同样能实现本项目，选 Vue 是"技术栈与问题形态的匹配 + 个人连续性"，不是"React 做不了"——这个判断本身也是一种工程决策能力（对应设计文档 ADR 思路）。

**A2. 为什么用 ECharts，不用 D3 或 Three.js？**

- 定位不同：ECharts 提供的是"图表级"抽象（地图 geo + visualMap + effectScatter 涟漪散点开箱即用），D3 提供的是"原语级"抽象（要自己实现坐标、比例尺、动画、图例），同等视觉与交互工作量至少数倍；
- 需求决定选型：本项目需要 6 类图表（Map/Bar/Pie/Line/Heatmap/EffectScatter）+ 深度定制视觉，ECharts 的注册机制（按需 use、registerTheme、registerMap）恰好都能覆盖；
- Three.js 是 3D 场景引擎，本项目是 2D 地图 + 统计图表，引入 3D 属于过度设计且牺牲可维护性；
- 体积已控制：按需引入后 echarts chunk 617KB（gzip 206KB），不是"偷懒用全家桶"。

**A3. 为什么用 Pinia，不用 Vuex 或事件总线（EventBus）？**

- Vuex 在 TypeScript 下需要大量类型体操（mutation/getter/root 类型穿透），Pinia 是 Vue 官方推荐的下一代方案，setup store + TS 严格模式零摩擦；
- 事件总线是本项目架构的**反面教材**：12 个组件网状通信、状态散落、不可追踪、解除过滤时必然状态漂移——SSOT 架构（ADR-4）正是为了消灭它；
- Pinia 与 Vue DevTools 集成，Store 状态变化可时间旅行回放，联动调试效率高；
- 本项目单 Store 即可承载（snapshot + 三个过滤维度 + 钻取栈），Pinia 的轻量性正合适。

**A4. 为什么用 hash 路由而不是 history 模式？**

- NFR-07 要求离线可运行：hash 路由的构建产物无论静态服务器还是本地 file 协议打开都能正确路由，**零服务器配置**；
- history 模式在静态托管下必须配置 fallback rewrite（否则刷新 /about 会 404），属于不必要的部署风险（ADR-2）；
- 本项目仅两个路由（`/` 主屏与 `/about` 说明页），无 SEO 需求，hash 的 URL 美观代价为零。

**A5. 为什么要上 TypeScript？还是严格模式？**

- 本项目有 8 类领域实体（省/市/路口/事故/流量/车辆类型/KPI 快照/趋势点）+ 12 个组件的 Props 契约 + Store getters——没有类型等于裸奔；TS 让这些契约显式化、编译期可查；
- 严格模式的实际收益：12 个组件都消费同一个 Store，改一个字段名，`vue-tsc --noEmit` 立刻把所有受影响位置报出来，重构是安全的；
- mock 引擎是纯 TS，可以被 esbuild 直接打包后独立跑 Node 单测（6 个自动化测试的技术前提）；
- 这也是设计文档里明确的 ADR-9 决策：类型契约是可答辩的工程亮点。

**A6. 为什么用 Vite 6，不用 Webpack？**

- 开发体验：esbuild 预构建 + 秒级 HMR，调试联动交互时改一行立即见效；
- 产物控制能力正好命中本项目两个刚需：JSON 超过内联阈值自动外置为**异步 chunk**（geoJSON 分片策略的技术基础）、vendor 拆包（echarts 独立 chunk 617KB/gzip 206KB）；
- Vue 官方默认工具链，与 vue-tsc、@vitejs/plugin-vue 无缝集成。

## B. 架构设计类（5 题）

**B1. SSOT 是什么？为什么对这个项目特别重要？**

- SSOT = Single Source of Truth，单一数据源：全部业务状态（当前数据快照、地区钻取栈、车辆类型、事故类型四个状态）只存在于一个 Pinia Store，组件不持有任何业务数据副本；
- 重要性一：**口径一致性**——KPI 卡的"今日事故数"和事故饼图的合计永远相等，因为它们读的是同一份 getter 派生结果（需求的数据质量约束 5 的代码级保障）；
- 重要性二：**联动可维护**——任何入口修改过滤条件只改 Store 一处，12 个消费组件自动同步，不存在"忘记通知某个图表"；
- 重要性三：**可测试**——过滤逻辑集中，可以针对 Store 直接写测试；
- 反例说明：如果每个组件自己记过滤状态，从 FilterTagBar 解除过滤时就会状态漂移——这是大屏联动的经典缺陷，我在设计阶段就用 ADR-4 把它排除掉了。

**B2. 为什么图表组件不允许自己过滤数据？**

- 一旦允许，同一份过滤口径就会有 N 份实现，聚合口径必然漂移（比如一个用四舍五入一个用截断，占比就不闭合了）；
- 我的规则：图表组件是"无业务状态的渲染器"，只接收 Store getters 派生好的 props；过滤和聚合只发生在引擎层与 Store 层；
- 由此获得架构红利：**换图表不动业务**（NFR-10 模块化）——未来加新图表只要消费现成 getter，业务逻辑零复制；
- 口径闭合不是口头保证：自动化测试 2 验证了类型求和 = 总量（误差 < 0.1%）、省求和 = 全国（误差 < 0.2%）。

**B3. mock 引擎为什么必须与 Vue 解耦？**

- 解耦是分层架构（L5→L4→L3→L2→L1 单向依赖）的直接结果：引擎在 L2，不知道 L3/L5 的存在；
- 收益一：**可独立单测**——esbuild 打包后直接跑 `node --test`，6 个自动化测试（实体规模/口径闭合/连续性/双峰/值域/暂停恢复）全部这样跑通，不需要浏览器与 jsdom；
- 收益二：**数据源可替换**——未来接真实 API 只替换 L2 的产出方式，Store 与全部组件零改动；
- 收益三：引擎逻辑是纯函数式的计算（时钟、噪声、聚合），无框架依赖时推理与调试都简单。

**B4. 组件之间怎么通信？为什么所有事件都要经过 ScreenView？**

- 两条铁律：上行"子组件 emit → ScreenView 接住 → 调用 Store action"；下行"Store getters → ScreenView 计算 → props 下发"；
- 这样组件之间**互相不感知**——事故饼图不知道地图存在，地图不知道排行存在，它们只认识 Store；
- 12 个组件若两两直连是 66 条边的事件网，经 ScreenView 收敛后是 12 条入边 + 12 条出边的星型结构，复杂度从 O(n²) 降到 O(n)；
- 失败兜底也走同一通道：geoJSON 缺失提示由 Store 的 mapMissingTip 状态驱动，组件自己不弹窗。

**B5. 为什么分五层？分层带来什么实际好处？**

- 五层 = 资源 / 数据引擎 / 状态 / 组合函数 / 视图，划分依据是"变化频率与职责"：视觉常变（L5）、业务状态少变（L3）、数据来源将来必变（L2）；
- 好处一：**可替换**——换数据源动 L2、换图表库动 L4/L1、改视觉动 L1 主题与令牌，影响面都锁死在自己层；
- 好处二：**可测试**——L2 独立单测、L3 集中测过滤、L1 是纯资源；
- 好处三：**答辩可讲**——每一层都能对应到需求（NFR-10 模块化）与具体文件，不是纸面架构。

## C. 数据类（5 题）

**C1. 数据是哪来的？是真实数据吗？**

- 直接坦诚（绝不含糊）：**全部数据由前端内置的模拟数据引擎离线生成，没有真实数据接口**——这是需求规格 1.3 节明确声明的范围边界（纯前端毕业设计方向，无自建后端）；
- 但"模拟"不等于"乱随机"：数据按真实交通规律构造——早晚双高峰、深夜低谷、拥堵指数与车速负相关、在途车辆高峰多于低谷、34 省按经济/人口量级赋权重（广东 1.00 基准）；
- 口径严格自洽：市级数据自下而上聚合成省级、全国级，各图表数值永远闭合；
- 引申：模拟数据引擎本身是我设计的工作量之一（噪声模型 + 聚合 + 断言），不是"应付"，见 C2/H2。

**C2. 如何保证数据的"真实感"和"连续性"？**

- **日内规律**：双峰函数 hourFactor = 0.16（深夜基线）+ 0.62·G(h;8,1.3)（早高峰）+ 0.78·G(h;18,1.6)（晚高峰，略高于早峰）+ 日间平台项——高斯核保证平滑无台阶；
- **连续性三层模型**：双正弦波（300s 慢波 + 40s 快波）给节奏感 → 有界随机游走（clamp 在 ±8%·base）给不可预测性 → 连续性钳制 clamp(raw, 0.85·prev, 1.15·prev) 兜底排除跳变；
- **实测数字**：需求约束相邻变化 ≤ ±15%，自动化测试实测**相邻快照变化 2.37%**；
- **相关性**：congestionIndex = f(hourFactor)，avgSpeed = 58 − 3.8·congestionIndex（拥堵 2 → 约 50km/h，拥堵 8 → 约 27km/h），在途车辆 ∝ hourFactor；
- 车辆类型还有差异化时段形状：公交车双峰更尖、货车是日间宽平台、电动车晚峰放大 1.2 倍——联动过滤后各类型热力形态不同。

**C3. 聚合口径怎么保证（KPI 和明细对得上）？**

- 机制上：**自下而上聚合**——省级/全国级指标从不直接生成，一律由下辖市（34 省含 66 个市级实体）逐级求和/加权平均算出；车速按在途车辆数加权平均；
- 代码上：聚合只存在于引擎层 aggregate 模块，图表层禁止聚合（B2 的 SSOT 延伸）；
- 验证上：开发期断言 + 自动化测试 2——Σ 车辆类型 activeCount = activeVehicles（误差 < 0.1%）、Σ 省值 = 全国值（误差 < 0.2%）、Σ 占比 = 100%；
- 路口实体也按"内置省每市 8~15 个 + 非内置省省会 3 个代表路口"构造，全国 TOP10 排行的真实性由 864 个路口实体支撑。

**C4. 为什么时钟要 60 倍加速？会不会让数据失真？**

- 动机纯工程：1 真实秒 = 60 模拟秒 → 24 分钟滚完 24 小时趋势窗口（288 点、5 分钟步长）、热力图"当前时段"每小时推进 1 分钟——**答辩十几分钟内评委能亲眼看到完整日内规律演变**（早晚高峰到来与消退），实时同步（1:1）则什么都看不到；
- 不失真：加速只作用于"时间流速"，hourFactor/噪声模型本身与真实时间无关；相邻快照连续性约束（±15%）按刷新周期独立成立；
- 参数集中在引擎 config（intervalMs / accel 可调，NFR-11），随时可切回 1:1；
- 顺带说明：accel 也是 ADR-7 的正式设计决策。

**C5. 事故数量是怎么生成的？为什么只增不减？**

- 泊松增量模型：每 tick 新增事故起数 ~ Poisson(λ)，λ ∝ 省权重 × hourFactor——高峰多、深夜少、大省多，符合事故发生率的经验规律；
- "今日事故数"是当日累计口径（从 0 点起只增不减，与真实统计口径一致）：引擎启动（bootstrap）时按"当日已流逝小时 × hourFactor 曲线积分"预置基数，之后每 tick 递增；
- 事故明细带类型（追尾/刮擦/侧翻/碰撞行人/其他）、严重程度、涉事车辆类型、坐标、处理状态——支撑散点过滤与饼图占比；
- 防膨胀：活跃事故列表封顶 200 条（超出按结案状态淘汰），保证长时间运行内存稳定（NFR-12）。

## D. 地图类（4 题）

**D1. geoJSON 是哪来的？版权有没有问题？**

- 来源：阿里云 DataV 数据可视化平台的公开行政边界数据（areas_v3 版本），是业界做中国地图可视化的通行公开数据源；
- 我写了专门的 CLI 脚本（`scripts/fetch-geo.mjs`）做获取与裁剪：只保留 name / adcode / center / centroid 四个字段，坐标不抽稀（保轮廓精度）；
- 裁剪效果显著：9 份边界（全国 + 4 省 + 4 省会市）实测总体积 **1.49MB**，明显优于设计阶段约 5MB 的预算；
- 用法合规：本地打包用于学术毕业设计，无商业分发问题。

**D2. 为什么只内置 4 个省？是不是没做完？**

- 这是有意的**设计决策**（ADR-3，需求方确认），不是烂尾：全量 34 省市边界约 30MB+，直接拖垮首屏 3 秒指标（NFR-01）；裁剪到 4 省 4 市后仅 1.49MB，且只加载全国图首屏 gzip 约 470KB；
- 4 个省的选择有代表性：广东（华南/经济第一）、江苏浙江（华东/城市群）、四川（西部/大地理尺度）——覆盖不同区域形态，证明钻取机制的通用性；
- 未收录区域不是"点了没反应"，而是走 FR-03 的**降级设计**：明确提示 + 列出可下钻清单 + 视图数据保持不变——把功能边界转化为交互引导；
- 扩展成本极低：跑一次 `node scripts/fetch-geo.mjs` 增加目标 adcode 即可纳入新省份。

**D3. 地图钻取具体是怎么实现的？**

- 状态侧：Store 里一个 `regionStack` 钻取栈（['CHINA'] → push 省 adcode → push 市 adcode），栈顶就是当前地区维度，逐级返回就是 pop——栈结构天然匹配 FR-04 的回退语义；
- 资源侧：`services/mapRegistry.ts` 用 `import.meta.glob` 生成懒加载器映射，点击时才动态 import 对应 geoJSON chunk → `echarts.registerMap(adcode, geoJSON)` → 已注册缓存判重（防重复注册泄漏）；
- 渲染侧：**切层不销毁实例**——只 `setOption({ series: [{ map: 新注册名 }] })` 原地换装，无闪烁、无泄漏、动画连贯（ADR-8）；
- 失败侧：未收录区域走 mapMissingTip 全局提示，栈不变。

**D4. "adcode 对齐"是什么？为什么重要？**

- adcode 是国家统计局/民政部行政区划编码（广东 440000、广州 440100 这样），DataV geoJSON 的每个 feature 都带 adcode；
- 我的方案：**业务实体统一以 adcode 为主键**，并维护 adcode → geoName 映射表，数据侧的名称一律经映射转换后再喂给地图；
- 重要性：ECharts 地图按 feature 的 `properties.name` 匹配数据，而 DataV 的 name 多为全称（"广东省""广州市"）——不做对齐就会出现**"数据有值但地图不上色"**的经典事故（设计风险清单 R1，我列为高危提前消解）；
- 收益：钻取、热力、散点全链路都建立在 adcode 上，两级钻取的父子关系（440000 → 440100）也由编码前缀天然表达。

## E. 性能类（5 题）

**E1. ECharts 按需引入到底省了多少？**

- 做法：`echarts/core` 的 `use([...])` 只注册 6 类图表（Bar/Pie/Line/Heatmap/Map/EffectScatter）+ 5 个组件（Grid/Tooltip/Legend/VisualMap/Geo）+ CanvasRenderer，代码里**禁止** `import * as echarts`（会破坏 tree-shaking）；
- 实测：echarts 独立 vendor chunk **617KB，gzip 后 206KB**——对比全量引入（echarts.min.js 约 1MB+、gzip 330KB+）实打实减掉约三分之一以上的传输体积；
- 注册入口收敛在 `chart/setup.ts` 单文件（R3 风险对策），不会出现"某个组件偷偷全量引入"破坏优化；
- 配合 geoJSON 异步分片，首屏 gzip 总量约 470KB，3 秒指标有余量。

**E2. 12 个图表同一个 tick 重绘，会不会卡？**

- 三重机制防卡：
  1. **merge 模式 setOption**——只更新变化的 series.data，不重建整棵 option 树，禁整屏 notMerge；
  2. **Vue 响应式批处理**——同一 tick 内 Store 状态只变一次，12 个组件的 watcher 合并到同一 flush 执行，天然合帧，不会排队画 12 帧；
  3. **KPI 数字用 CSS transition**——数值滚动零 JS 帧循环开销；
- 另有动画时长统一 ≤ 400ms（留 NFR-02 的 500ms 裕量）、辉光 shadowBlur 上限 12、effectScatter 涟漪散点限流；
- 结论：NFR-04 要求单次刷新主线程阻塞 < 100ms，实际体感远低于该值，60fps 无可感知掉帧。

**E3. 内存泄漏怎么防的？长时间运行会不会崩？**

- 泄漏源清单一一对应对策，全部收敛在三个地方：useECharts（实例 dispose + ResizeObserver disconnect + 防抖定时器 clear，卸载时原子完成）、引擎（全局唯一 interval，pause/路由离开均清理）、缩放 composable（resize 监听同生命周期移除）；
- 数据结构防膨胀：趋势**固定 288 点环形缓冲**（只滚动不增长）、活跃事故**封顶 200 条**、快照整体替换不追加历史；
- 地图切层复用实例不重建（防碎片）；路由离开 ScreenView 时引擎停止 + 全图表 dispose；
- 验证：NFR-12/AC-20 按"连续运行 2 小时含反复钻取、联动、暂停恢复"验收，帧率与内存稳定。

**E4. 整个大屏是 transform: scale 缩放的，tooltip 和点击坐标为什么是准的？**

- 原理：ECharts 底层 zrender 的事件定位基于 `getBoundingClientRect()`——它返回的是 transform 之后的**视觉盒**，zrender 用它和 canvas 内部像素做换算，所以 scale 容器下点击命中与 tooltip 定位天然正确；
- 过程严谨：这一点我在设计阶段列为**首个 spike 验证项**（风险 R5），先做了最小验证 demo 才铺开全屏方案——"先证明再铺开"，不是碰运气；
- 顺带讲选型（ADR-1）：rem 不会自动缩放 ECharts 内部字号/半径，vw 在非 16:9 窗口横向溢出，transform 对 DOM 和 canvas 一视同仁且实现收敛在一个 composable。

**E5. 首屏体积和加载时间到底是什么水平？**

- 实测构成：主 bundle（Vue + Pinia + router + 按需 ECharts）+ 首屏即需的全国 geoJSON，**首屏 gzip 约 470KB**；echarts vendor chunk 617KB（gzip 206KB）；
- 分片策略：4 省 4 市边界共 1.49MB 全部是**异步 chunk**，只有下钻到对应区域那一刻才加载（本地静态资源，无网络往返）；
- 结论：NFR-01 要求 3 秒首屏，本地环境实际体感 1~2 秒级（演示脚本步骤 1 现场可复现：刷新一次计时）；
- 若被追问"还能怎么优化"：地图边界可再抽稀/换 protobuf 格式、KPI 卡可做骨架屏——已列入展望。

## F. 功能扩展类（4 题）

**F1. 要接入真实数据，需要改哪里？**

- 只动 **L2 数据引擎层**：把 MockEngine 的 onSnapshot 回调替换为真实数据源（API 轮询或 WebSocket 推送），Store 的 applyTick 接口不变，**12 个组件与全部图表零改动**——这就是五层单向依赖 + SSOT 的架构红利，也是答辩最值得强调的扩展性证据（完整契约见 `design/api-contract.yaml`）；
- 需要补齐的配套：真实数据的字段映射（对齐我定义的快照 schema）、时钟基准换成服务器时间、聚合逻辑视后端能力选择前置或保留前端；
- 风险预告：真实数据的连续性不再由我的噪声模型保证，需在后端或接入层做同样的平滑/钳制处理，否则跳变问题会回来。

**F2. WebSocket 具体怎么接？**

- 替换点明确：`engine.start(callback)` → `ws.onmessage`（解析消息 → 产出同 schema 的 Snapshot → 调 store.applyTick），Store 与组件层完全无感；
- 工程要点：心跳保活、断线重连（指数退避）、降级策略（WebSocket 不可用时回退 HTTP 轮询）、消息乱序/去重处理；
- 暂停功能语义保留：暂停时前端只冻结渲染消费，不退订连接；
- 说明范围：WebSocket 本身在需求 1.3 是明确范围外（防范围蔓延），但架构上已预留——这叫"范围裁剪决策"，不是"做不了"。

**F3. 要加一个新图表，需要写什么？**

- 四步且只动增量：①`components/charts/` 新增一个 .vue 组件（useECharts + props 契约 + option 工厂）；②ChartCard 包裹（视觉自动统一）；③Store 加一个 getter（过滤维度沿用现有三维，逻辑复用）；④ScreenView 挂载传 props；
- **不需要改任何现有图表**——因为过滤口径在 Store 集中实现，新图表消费现成 getter 就自动获得全屏联动能力；
- 这就是"图表是无业务状态渲染器"（B2）的直接收益，也是 NFR-10 模块化的验收方式。

**F4. 移动端适配打算怎么做？**

- 诚实定位：当前是**有意的范围外**（需求 1.3 明确"仅面向桌面浏览器与鼠标交互"），大屏产品的主场景就是指挥中心大屏；
- 若做的技术路线：①版式层重写——ScreenLayout 的 grid-template-areas 换移动版式（优先保留地图 + KPI，专题图表折叠/Tab 化）；②交互层把 click 换 touch 事件；③缩放基准调整为移动设计稿或改 rem 流式；④ECharts 移动端本身支持触摸；
- 工作量评估：架构上组件/Store/引擎全部可复用，主要工作是版式与交互层，属于可控增量。

## G. 论文/学术类（4 题）

**G1. 你的创新点是什么？**

- 定位清晰：这是工程实现类毕业设计，创新是**工程方法层面的三个自研设计**，不宣称算法理论创新：
  1. **离线地图钻取方案**：geoJSON 裁剪 + 异步 chunk 分片 + 注册缓存 + 降级提示的完整离线地图工程（1.49MB 支撑三级钻取，断网可用）；
  2. **SSOT 三维联动模型**：钻取栈 + 双类型维度的集中状态架构，12 组件全联动且口径由构造保证一致；
  3. **数据连续性方法**：双正弦 + 有界随机游走 + 双重钳制的噪声模型，约束 ±15% 实测 2.37%，且暂停冻结时钟实现无缝恢复；
- 另一层面：EARS 需求（33 条）→ 五层架构 → 9 项 ADR → 自动化测试的**全链路工程规范**本身是方法论贡献；
- 诚实边界：不与学术论文比理论 novelty，与工程实践比完整性与严谨性。

**G2. 和现有的成熟大屏产品（DataV、帆软 FineReport 等）有什么区别？你做这个的意义？**

- 那些是**平台/工具**：配置式拖拽出大屏，产出物是配置；我的是**自研工程**：从需求到代码逐层实现，产出物是可维护、可测试、可扩展的代码架构；
- 研究点不同：平台关心"快速出页面"，我关心三个底层问题——联动状态如何不漂移、实时数据如何不跳变、地图与图表如何离线高性能共存；
- 类比：用 DataV 搭大屏像是用 WordPress 建站，我的工作像是手写框架实现——前者快，后者让你真正理解每一层为什么这样设计；
- 意义：毕业设计的目的就是训练完整工程能力，平台的"配置能力"无法替代这种训练。

**G3. 工作量怎么体现？**

- 文档链：395 行 EARS 需求规格 + 674 行技术设计（含 9 项 ADR、10 项风险清单）+ 需求追踪矩阵 + 任务分解与自测清单；
- 代码量与结构：约 30 个源文件——12 个视图组件、2 个 composables、1 个 Pinia Store、5 模块 mock 引擎（constants/entities/noise/aggregate/engine）、地图注册服务、自研 ECharts 霓虹主题、按需注册入口、领域类型定义；
- 自研工具链：geoJSON 获取裁剪 CLI（fetch-geo.mjs，支持 --force/--list/--dump-centroids）；
- 质量保障：6 个自动化测试 + vue-tsc 严格检查 + 21 个验收场景人工核验；
- 数据工程：34 省/66 市/864 路口实体体系与自下而上聚合管道。

**G4. 测试是怎么做的？覆盖够吗？**

- 三层测试体系：
  1. **自动化单元层**：mock 引擎因与 Vue 解耦，esbuild 打包后跑 Node 原生 test runner，6 个测试全过——实体规模（34/66/864）、口径闭合（<0.1%/<0.2%）、连续性（2.37%）、双峰特征（峰>谷×2.5）、值域约束、暂停恢复；
  2. **类型层**：`vue-tsc --noEmit` 严格模式全量检查；
  3. **验收层**：21 个 AC 场景（15 功能 + 6 非功能，含断网、多分辨率、2 小时长跑）逐条人工执行；
- 诚实边界：UI 交互层未引入 E2E 框架（如 Playwright），靠验收场景清单覆盖——若继续完善，E2E 化是第一优先级（可顺势讲展望）。

## H. 压力/刁钻类（5 题 · 回答策略：不辩解、给证据、留台阶）

**H1. "这不就是套了个模板吗？"**

- **策略**：不情绪化反驳，用**证据链**回应，语气平静自信；
- 第一句："这个系统没有任何一行代码来自大屏模板——我可以现场打开任意源文件给您看。"
- 证据链四连：①从零走完全流程：EARS 需求规格 33 条 → 五层架构设计 → 9 项决策记录；②视觉系统自研：ECharts 用的 neon 主题是我定义注册的（非官方主题库），五级色带是自建设计令牌；③核心逻辑自研：噪声模型有数学推导与公式实现、SSOT 联动架构有 ADR 论证；④质量可验证：6 个自动化测试 + 类型检查 + 21 验收场景；

- 现场杀手锏：邀请评委任选一个功能，现场打开对应源码走读。

**H2. "mock 数据算不算造假？"**

- **策略**：先承认事实、再重新定义问题——"造假"的前提是**冒充**，我从头到尾都在声明这是模拟；
- 第一句："我在需求规格第一页就写明了'全部数据由模拟引擎离线生成、无真实接口'——这是公开的研究边界，不是隐瞒。"
- 三层递进：①这是选题定位：纯前端毕业设计，研究的是可视化工程（联动/性能/离线），数据源本来就是变量而非常量；②类比学术惯例：风洞试验用模型飞机、仿真学科用模拟输入——**研究对象是系统行为时，受控的模拟输入正是方法论**；③模拟引擎本身是工作量：噪声模型、口径闭合、断言测试，工程含量不输接一个现成 API；
- 反守为攻（礼貌版）："如果接入真实数据，我的架构只需要替换 L2 一层——这恰好说明我没有把系统'焊死'在模拟数据上。"

**H3. "为什么不做后端？是不是能力不够？"**

- **策略**：把"没做"讲成"设计选择"，用深度对冲广度质疑；
- 第一句："这是和导师确认过的选题定位——毕业设计的深度在前端工程，后端会稀释这个深度。"
- 三个论点：①本项目的前端难点足够深：12 组件联动架构、离线地图工程、实时数据连续性、性能与内存治理——每一项都有完整的设计决策与验证；②架构上我为后端预留了干净接缝（L2 可替换、applyTick 接口稳定），"没做"不等于"做不了"；③工程判断力：有限时间内把一个方向做到可验收的深度，比铺十个浅坑更接近真实工业实践；
- 语气要点：自信但不傲慢，结尾可以说"当然，如果后续继续迭代，接入真实后端正是展望的第一步"。

**H4. "ECharts 是现成的库，你的贡献到底在哪？"**

- **策略**：类比 + 清单——库是工具，工程是贡献；
- 第一句："就像用 React 不等于项目没有含金量——库解决的是'画一个图表'，我解决的是库不负责的系统问题。"
- 贡献清单（对准 ECharts 不管的事）：①数据从哪来——自研模拟引擎（噪声模型/聚合管道/口径断言）；②12 个图表怎么协同——SSOT 联动架构；③地图怎么离线——geoJSON 裁剪/分片/注册/降级方案（ECharts 5 连中国地图都不内置）；④性能怎么保障——按需引入（617KB/206KB）+ merge 重绘 + 内存治理；⑤视觉体系——自研 neon 主题与五级色带设计令牌；
- 收尾："ECharts 负责最后 5% 的渲染，前面 95% 的系统设计是我的毕业设计。"

**H5. "断网演示是不是提前准备好的？数据是不是写死的？"**

- **策略**：欢迎现场验证——可证伪性就是最好的证明；
- 第一句："欢迎您现场验证——数据是每 5 秒由引擎实时计算的，不是写死的序列。"
- 验证方式三选一（现场主动提议）：①刷新页面后观察数值与刷新前不同（每次 bootstrap 重新演化）；②让我现场点"暂停/恢复"，冻结与续推的数值轨迹是连续的（写死数据做不到任意时刻冻结）；③打开 DevTools Network 面板——Offline 下依然刷新，且整个系统零网络请求（数据不可能来自外部缓存）；
- 技术依据：数据由 setInterval 驱动的实时计算产出（双正弦相位随模拟时钟推进），支持固定随机种子仅为"答辩可复现"的可选特性——**可复现是特性，不是作弊**。
